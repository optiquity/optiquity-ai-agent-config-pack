**BD-224 — Expand the `/pack-*` slash-command set + improve `/pack-help` coverage (brainstorm-gated)**
Type: feat — pack CLI UX / command surface. Add net-new `/pack-*` slash commands and close `/pack-help` coverage gaps so pack operators discover and invoke pack capabilities more easily. Opened 2026-06-15 (user direction). Pipeline: **brainstorm/discovery (researcher + architect) → user adjudicates the command set → architect design → planner → coder → bounded review/fix.**
Status: Open
Target: v11.0 — **scheduled JUST BEFORE v11.0 closeout** (user 2026-06-15) so the command set is designed against the SETTLED pack surface (after the major surface-changing v11.0 work lands), not a moving target.
Blockers: SEQUENCING (not technical). Runs near v11.0 closeout, AFTER the surface-changing v11.0 work settles — notably BD-221 (the Gemini→Antigravity conversion actively reshapes the command/skill trinity across `.claude`/`.codex`/`.gemini`→Antigravity) and the other v11.0 features (BD-206/171/210). Lands BEFORE BD-205 (the final readiness audit) so the audit covers the new commands. The Stage-1 brainstorm MAY run earlier if useful, but the chosen-set freeze + implementation wait for the settled surface.
Unblocks: faster, more discoverable pack operation — slash commands for common flows that today require knowing the `pack` CLI verbs or internal skills; a `/pack-help` that actually covers the full command surface.
Description:
  **Problem:** the `/pack-*` slash-command surface is thin (`/pack-help`, `/pack-startup`) relative to the pack's capability set (the `pack` CLI verbs in `scripts/pack-help.sh`, the operating flows). Operators must know internals to do common things, and `/pack-help` coverage has gaps (commands/flows not surfaced in help).
  **Stage 1 — BRAINSTORM / DISCOVERY (decision gate; user adjudicates the set):** per user direction 2026-06-15 the discovery is a `pack-docs-researcher` + `pack-architect` pass: (a) the researcher INVENTORIES the current `/pack-*` command surface + `/pack-help` coverage + the underlying `pack` CLI verbs, and surveys external CLI-UX command-discovery patterns; (b) the architect BRAINSTORMS candidate net-new `/pack-*` commands + candidate `/pack-help` coverage gaps, each with rationale + the flow it serves. Pack Chat surfaces the candidate menu to the USER, who decides the final set to build. NO design/implementation until the user freezes the set. (Mirrors the BD-221 Phase-0 decision-gate pattern: generate options → user adjudicates → freeze.)
  **Stage 2 — design → plan → implement** the chosen commands + `/pack-help` updates (architect design → planner → coder → bounded review/fix), under the **trinity rule** (each new command has cross-CLI parity across Claude / Codex / Antigravity, or a justified tool-specific exception) and the **skill `x-` contract** (`skill-agent-maintenance-mechanical`).
  **Execution-foundation requirement:** adding OR updating a `/pack-*` command is NOT merely adding/editing command text in a skill/doc/config. Each net-new command REQUIRES building its full execution foundation — the skill body's concrete steps + any new `pack` CLI verb/script it invokes; a command with no working execution foundation is not shippable.
  **Existing-command refresh (IN SCOPE):** review, update, and where useful EXPAND the EXISTING `/pack-*` commands + their skills (`/pack-help`, `/pack-startup`, and any others) to reflect the current post-v11.0-surface-change pack state — correct stale steps/outdated references, close coverage gaps beyond just `/pack-help`, and refresh each command's execution foundation where the underlying flow/verb changed. The whole existing command surface must be accurate, not only the net-new additions.
  **Out of scope:** changing existing command behavior beyond coverage/help; the BD-221 conversion itself; project-side (client `project-template/`) command surfaces unless the brainstorm explicitly scopes them (pack-self vs client command surfaces are SEPARATE — `pack-project-separation-of-concerns`).
  **Hard constraints:** trinity parity for every new command; each new command ships its EXECUTION FOUNDATION (the skill body's concrete steps + any new `pack` CLI verb/script it invokes), not merely command text — a command with no working foundation is not shippable; existing `/pack-*` commands (incl. help) reviewed + brought current, not just net-new added; `/pack-help` remains the single discovery surface; no boundary leak between pack-self and client `project-template/` command surfaces; the brainstorm's chosen set is FROZEN before Stage-2 design; designed against the settled (post-major-v11.0-work) surface.
  **Acceptance criteria (provisional — refined by design):** a user-adjudicated set of net-new `/pack-*` commands implemented with trinity parity, each shipping a working execution foundation (skill body + any scripts/verbs); existing `/pack-*` commands reviewed/updated to current state (stale steps/references corrected); `/pack-help` + other coverage closes the agreed gaps and reflects the current surface; `validate-pack` green; full CI battery green; no client-install/boundary regression.

Render-cache + payload-thinning refinement (2026-07-18, user-approved design — lands as in-scope BD-224 umbrella work, not a new BD): the `/pack-dashboard` render (a BD-224 net-new command) is refined so its state-independent HTML shell is persisted and reused instead of regenerated on every render.
  **Render-cache:** the shell (skeleton + inline CSS + render JS + hash router) is a git-tracked, spec-fingerprinted file `pack-ops/dashboard-approvals/dashboard-shell.html`; each render REUSES it when its embedded `spec-sha` matches `git hash-object pack-ops/DASHBOARD-SPEC-PACK.md` and REGENERATES it only when the build-spec's content changes (or the shell is absent). Script-free / agent-driven (Read/Bash/Write); deterministic (content-derived hash, no clock).
  **Payload thinning:** each render collects live state fresh and thins it — FULL `bds{}` records for in-window BDs (the running `motion[]` window plus any BD with a live deep plan), MINIMAL records for out-of-window (archived / resolved / deferred) BDs — then injects it into a copy of the shell to write `dashboard.html`.
