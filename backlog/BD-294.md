**BD-294 — The shipped trinity instructs an edit the graft engine cannot accept, and the graft's documented order-independence does not hold: fix the contract collision + ship a one-time in-place remediation for already-migrated clients**
Type: bug — trinity template ↔ customization-preservation contract collision (client-shipped surfaces; reported from a completed real-client v11 migration).
Status: Open
Target: v11.0
Blockers: None for the measurement stages. The D3 DIRECTION is a user decision taken after the architect measures the options (recorded in Position); it does not block the researcher or the measurement passes.
Unblocks: a client that can follow the trinity template's own instruction and still graft cleanly on every future update — and an already-migrated client that can reach that state in place, without re-migrating.
File/Symbol: `project-template/CLAUDE.md` + `AGENTS.md` + `GEMINI.md` (the preamble identity block above the first H2, and the in-section `[PLACEHOLDER — fill in]` bodies); `scripts/lib/marker-preserve.sh` (the `marker_preserve_trinity` engine and its L-1/L-2/L-6/L-8 rules); the marker-section skill contract that documents order-independence; `project-template/skills/resolve-merge-conflicts/SKILL.md`; `supporting-docs/MIGRATION-v10-to-v11.md` (the remediation recipe's home) — docs-researcher census completes the set.
Description:
  **The collision (report family D3 — the most consequential finding).** The shipped trinity opens with an identity block (`**[PROJECT_NAME]** targets [PLATFORM_TARGETS].` and a transport line) carrying the instruction *"Fill in placeholders and remove this block."* Both ways of complying fail the marker engine, verified by the client round-tripping through `marker_preserve_trinity`: filling in place yields `customization-detected-needs-reconciliation` (pack-owned preamble diverges out-of-marker, L-8); filling inside a project-owned marker pair yields a well-formedness failure (L-6/L-1: a project-owned marker region with no enclosing H2, because it sits above the first H2). Measured pack-side: the identity line is at `project-template/CLAUDE.md:26` and the first H2 is at line 29 — the preamble genuinely sits above the first H2, which is why no marker is admissible there. So a client that FOLLOWS the shipped instruction can never graft cleanly again, and a client that IGNORES it ships context files telling every agent, every session, that the project is named `[PROJECT_NAME]`. The same pattern recurs in section bodies (`[PLATFORM_DEFAULTS — …]`, `[GRPC_RULES — … or delete section]`, `[PLATFORM_SECURITY — …]`), where filling or deleting is the same divergence.
  **The second defect (report family D5).** The marker skill states section ORDER is not enforced — the engine compares sections by heading NAME, so a reordered-but-complete fold still passes. The client observed otherwise, reproducibly across all three trinity files: an identical fold (same marker regions, same `renamed-from` annotations, same content) verdicts `customization-detected-needs-reconciliation` when Shape B blocks are appended at end of file, and `merged-with-customization` when they sit at the position of the section they suppress. Either the engine has a position dependency the docs deny, or the documented contract is wrong — determining WHICH is the first measurement, since it decides whether this is a code fix or a doc fix. This is the same defect class the recent CI-guard work addressed: a documented contract the code does not honor.
  **Remediation is in scope and is a deliverable.** Unlike the source-side fixes in the sibling entry, an already-migrated client's trinity is genuinely divergent — they filled the placeholders, that content is theirs, and no update-path classification can absorb it. Whatever direction D3 takes, it MUST ship with a one-time, in-place remediation recipe that converts an existing filled-in trinity to the resolved shape without re-migrating, verified against the real reported shape (placeholders filled in the preamble, trinity otherwise pack-canonical). The recipe is a shipped client deliverable, not a note in a pack record.
Acceptance criteria: the D3 direction is chosen by the user from architect-measured options, each option's blast radius on EXISTING installs measured before the choice; after the fix, a client that follows the trinity's own instruction grafts cleanly — proven by round-tripping the filled-in shape through the engine and observing a clean verdict, not by inspection; the in-section placeholder bodies are covered by the same resolution or explicitly scoped out with evidence; D5 is resolved in the direction the measurement dictates (engine fix if the position dependency is real, doc fix if the contract is wrong) with a regression test that BITES on the reported reproduction; **a one-time in-place remediation recipe ships and is PROVEN on a scratch clone of an already-migrated client tree — the trinity reaches the resolved shape with no re-migration and no loss of the client's filled-in content**; full CI battery green.
References: the client defect report families D3 and D5. The sibling entry carries D1/D2/D4/D6 (source-side install fidelity + the `--update` remediation path); the two are sequenced so the source-side fixes can land without waiting on this entry's design work.
Position: v11.0 — launch-gating. Every new client hits D3 on day one, and it cannot be worked around: both ways of complying with the shipped instruction are defects. Runs the LARGE deterministic pipeline. The D3 direction (make the preamble marker-eligible / relocate the identity line below the first H2 / teach the graft that placeholder-filling is expected divergence) is a USER decision at the design review, made after the architect measures each option's effect on existing installs — the relocation option changes the shipped trinity's shape for every future client, while the engine option changes preservation semantics.
