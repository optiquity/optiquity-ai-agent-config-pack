**BD-279 — Code-optimization methodology: skill(s) + existing-agent pipeline for intentional net-positive refactors of EXISTING code (pack + project, mirror-but-customize)**
Type: design investigation → methodology skill(s) + pipeline wiring (project-side shipped deliverable + pack-side internal). Investigate-then-implement: docs-researcher census → architect design (decomposition decision) → user design gate → planner → coder waves. No code lands until the user approves the design.
Status: Open
Target: v11.1 (user-directed 2026-08-02; explicitly NON-BLOCKING for v11.0). Originated as a Pack-Chat design discussion; opened as a scoped v11.1 BD so the thinking is not lost. The design pipeline runs when v11.1 is the active version — NOT now.
Blockers: SEQUENCING (not a hard dependency). Best designed AFTER the v11.0 project-side agent/skill ecosystem SETTLES — the optimizer must pressure-test against the FINAL project-side agent roster + skill set, which is still moving under v11.0 (BD-109 adds a 17th project agent; BD-205 readiness sweep; BD-210 maintenance-docs cleanup). Running the design pipeline before settle would design against a stale ecosystem. Not started until v11.1 active.
Unblocks: intentional, net-positive optimization of EXISTING pack + project code — latency reduction, execution speed, encapsulation, simplification, UX, code/design-pattern re-use, introduction of good patterns — WITHOUT churn or anti-pattern risk, on both surfaces.
File/Symbol (TBD at design time — decomposition is the PRIMARY open question, below): candidate surfaces — a pack-side optimization-methodology skill + a SEPARATE project-side optimization-methodology skill (shipped, × 3 CLIs) or skill-SET; per-expertise catalogs; wiring into the EXISTING architect / coder / reviewer on both surfaces (pack `pack-*`, project shipped roster). NO new agent by default. The exact file set is an OUTPUT of the architect's decomposition decision, not presumed here.
Description:
  **Problem:** the pack has no codified methodology for optimizing EXISTING (working) code. Optimization is high-risk without a framework: it easily becomes CHURN (refactor-for-its-own-sake) or trades a marginal win for undesirable complexity / a broken design. There is today no shared contract for "is this refactor net-positive?" and no guardrail against optimizations that introduce anti-patterns.
  **Goal:** a methodology that produces INTENTIONAL, NET-POSITIVE refactors — benefits measurably exceed drawbacks — and that NEVER forces or introduces a bad design. Benefits in scope: latency reduction, code-execution speed, encapsulation, simplification, UX improvements, code re-use, design-pattern re-use, introducing good design patterns, and similar enhancements. HARD guardrails (veto): NEVER introduce a bad design, anti-patterns, encapsulation violations, inheritance violations, polymorphism violations; NEVER break common design patterns, break code re-use, or add undesirable complexity for a small benefit.
  **Recommended shape (from the originating discussion — a STARTING HYPOTHESIS for the architect to pressure-test, NOT a presumed answer):**
    - **A SKILL (methodology), not a new agent — default.** The pack grain is "agents = WHO (role / lane / tools), skills = HOW (reusable methodology)." Optimization is a HOW: the reasoning it needs is the design-discipline judgment the EXISTING architect / reviewer already carry. A new agent re-scopes that same judgment behind a new persona = role proliferation. Add an agent ONLY if a genuinely distinct toolset (profilers / benchmarking / instrumentation harnesses the current agents lack) later justifies it — and even then prefer extending an existing agent's tools + a skill over minting a role. [architect to confirm against the real ecosystem.]
    - **Core contract the skill encodes:** (a) a NET-POSITIVE LEDGER per candidate refactor — an explicit benefit-vs-drawback accounting with evidence (modeled on the architect's Empirical-Evidence Block); no measured net benefit ⇒ REJECTED; (b) the BENEFIT TAXONOMY above; (c) a GUARDRAIL VETO CHECKLIST (the hard "never" list above) — a small win with a complexity / anti-pattern tax FAILS; (d) a CONSERVATIVE DEFAULT — "leave it alone unless the win is clear and measured" (the optimizer's failure mode is churn; the default answer is no-change).
    - **Invoked by the EXISTING pipeline, gated by the user:** architect (produces the RANKED ledger of candidate refactors, read-only) → **USER GATE** (approves WHICH refactors — the anti-churn THROTTLE; optimization is discretionary, so approving the refactor SET before any code is the single most important control) → coder (implements approved refactors, bounded review/fix cycle) → reviewer (ADVERSARIALLY verifies each refactor actually delivered the claimed benefit AND introduced no regression / anti-pattern — the guardrail ENFORCER). So the answer to "design only or coder too?" is BOTH — through the existing agents, user-gated.
  **PRIMARY DESIGN QUESTION — skill decomposition (the headline the pipeline must resolve first):** ONE general optimization skill, or MULTIPLE expertise-scoped skills — and on WHICH axis?
    - The DECISION FRAMEWORK (ledger, guardrails, forward-looking scan, user-gate) is UNIVERSAL. But the requirements differ deeper than a catalog: the EVIDENCE BASE and the REVIEWER LENS differ by CONCERN — a UX optimization is judged on user-flow / latency-PERCEPTION / accessibility; a Swift ARC / retain-cycle fix on memory-graph + profiler data; a system-design refactor (module coupling, dependency inversion) on architecture metrics (largely language-agnostic); a proto / API change on wire-compat + streaming semantics.
    - Candidate split axes (architect decides): by LANGUAGE (Swift / Python / gRPC-proto) — misses cross-language UX + system-design; by CONCERN (performance / encapsulation-&-system-design / UX / API-design) — matches the differing evidence bases + reviewer lenses, with language as a SUB-catalog inside "performance"; by LAYER (code-level micro-opt vs system-level design) — clean but coarse.
    - LIKELY shape: HUB-AND-SPOKE — one core methodology skill (the universal contract) + expertise SPOKES. The originating discussion's INSTINCT was to split by CONCERN (language as a sub-catalog) because the METHODOLOGY of proving net-positive differs by concern more than by language — but this is an explicit HYPOTHESIS, not a decision. The docs-researcher CENSUSES how existing pack + project skills/agents are decomposed (methodology-vs-catalog, and on what axis); the architect DECIDES the decomposition + axis. NOT presumed single or many.
  **Pack-side vs project-side — SEPARATE skills (mirror-but-customize, NO dual-use per `dependency-direction-placement`):** the two surfaces optimize different things for different audiences:
    - **Pack-side** target = the TOOLING (`validate-pack.py` checks, bash, the migrator framework, renderers). "Latency" ≈ CI-check runtime. Audience = pack developers. THIN skill: much of pack-side optimization discipline is ALREADY codified as memories — `ci-check-runtime-compounding` (cheap-per-invocation), `ci-guard-design-measure-then-bound` (git-tracked scan, not filesystem walk), `dependency-direction-placement` (no dual-use, boundary) — so the pack-side skill mostly POINTS AT these rather than re-authoring them.
    - **Project-side** target = the CLIENT's Swift / Python / gRPC APPLICATION code. "Latency" = real end-user-facing performance + UX. Audience = the client's developers + their end users. SUBSTANTIAL skill: this is the real deliverable — it SHIPS to clients (× 3 CLIs), must honor the `x-` client contract, and must COMPOSE with the existing project reviewer / architect (and consider formalizing / composing with optimization-adjacent review lenses rather than reinventing — e.g. type-design / simplifier / silent-failure analogs).
    - Per no-dual-use: a SEPARATE pack-side copy and a SEPARATE project-side copy, even where the core framework is conceptually shared — never one file serving both.
  **Forward-looking (the optimizer must be well-informed by queued work) — a STEP in the methodology, not a new capability:** before proposing a refactor, scan the queued backlog / implementation-plan entries + the graphify blast-radius. Two rules fall out: (1) DON'T optimize code that a queued feature is about to rewrite; (2) optimize TOWARD the direction queued designs are heading, not against them. This is `cross-bd-collision-scan` (intersect blast-radius with open work) + `graph-first-context` (blast-radius / "what depends on this") APPLIED to optimization — mechanisms that already exist.
  **Design principles (load-bearing):** the USER GATE is the anti-churn throttle; the REVIEWER is the guardrail enforcer; the DEFAULT is no-change (conservative bias); every refactor carries an evidence-backed net-positive ledger; nothing is auto-optimized.
  **Open questions for the design pipeline (docs-researcher censuses; architect decides):**
    1. Skill decomposition + axis (the PRIMARY question above) — single vs many; language / concern / layer.
    2. New agent vs skill vs both — confirm skill-not-agent against the real ecosystem; does any distinct toolset (profilers / benchmarks) justify extending an agent's tools or a new agent?
    3. Catalog structure — expertise catalogs as skill SECTIONS vs SUB-skills vs reference docs the skill cites.
    4. Exact pack/project boundary — how much the pack-side skill merely REFERENCES existing memories vs adds new content; the project-side skill's composition with the shipped project reviewer/architect + the `x-` contract.
    5. Where the user-gate + net-positive-ledger + guardrail contract LIVE — inside the skill vs a new pack rule / memory.
    6. Whether/how to compose with (or formalize) existing optimization-adjacent review lenses instead of reinventing them.
  **Process (required flow, at v11.1):** the large-BD pipeline — `pack-docs-researcher` census (existing pack + project agents/skills, their decomposition axes, the optimization-adjacent review lenses, the benefit/guardrail vocabulary) → `pack-architect` design against the SETTLED v11.0 ecosystem (resolves the decomposition + all open questions, measure-then-bound) → adversarial architect → reconciliation (if findings) → USER design gate → `pack-planner` → adversarial planner → reconciliation (if findings) → USER planner-to-coder gate → parallel/serial coder waves. Not started until v11.1 is active.
Acceptance criteria: (at v11.1) an architect design doc maps the optimization-methodology landscape with measured evidence — resolving (i) single-vs-many skill decomposition + axis, (ii) skill-vs-agent, (iii) catalog structure, (iv) the pack/project split, (v) the forward-looking mechanism, (vi) where the net-positive/guardrail contract lives — and recommends a coherent strategy following measure-then-bound; a USER decision is recorded (including "no change" for any sub-part that is justified); if implementation is approved, the skill(s) + pipeline wiring land with EVERY encoding surface in lock-step (the skill(s) × 3 CLIs where shipped, any new rule/memory, the `x-` contract, cross-ref docs, tests); NO dual-use (separate pack + project copies); the project-side deliverable honors the `x-` client contract; `validate-pack` green.
Non-goals (explicit): (a) NOT a v11.0 deliverable (user-directed v11.1, non-blocking); (b) NOT a new agent by default (skill-first; agent only if a distinct toolset justifies it); (c) NOT auto-optimization — every refactor is USER-GATED; (d) NOT churn — a marginal win with a complexity / anti-pattern tax is rejected, not shipped; (e) NOT a change to WHERE code/discipline lives beyond what an approved refactor entails.
