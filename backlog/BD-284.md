Meanwhile the migrator is automation-friendly (bare = dry-run+apply), so the interactivity vs automation asymmetry between the two paths is reversed and confusing (friction F2).
  **Goal:** add `--yes` (bypass the confirm, for automation); make `confirm_proceed` TTY-aware (a non-TTY invocation without `--yes` still declines, but the decline message NAMES `--yes`); adopt the same tri-state vocabulary the migrator interactive mode (BD-283) uses. Extract the tracker-init interactive idiom into a small shared `scripts/lib/prompt.sh` that BOTH `init-project.sh` and the migrator source — fixing F2/F3 with minimal blast radius. Do NOT unify the reconciliation ENGINES (install uses `existing_classifier_copy`/`three-way.sh`; migration uses `customization_preserve`) — share only the prompt/UX skin.
  **Scope note:** contract-preserving — the default flow (TTY, no `--yes`) still shows the preview + confirm; `--yes` is purely additive.
Acceptance criteria: `init-project.sh --yes` installs without prompting; a non-TTY invocation without `--yes` declines with a message naming `--yes`; `scripts/lib/prompt.sh` exists as the shared tri-state helper (sourced by init-project + ready for BD-283); `INSTALL-PROCEDURES.md` updated in lock-step; `test-init-project.sh` covers `--yes` + the non-TTY decline message; `validate-pack` (both jobs + `PACK_VALIDATE_DEEP=1`) + the persona-contract suite green; the default install flow unchanged.
