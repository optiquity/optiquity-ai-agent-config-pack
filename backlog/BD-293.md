**BD-293 — A correct v11 install fails the pack's own client doc-gate, and `--update` cannot deliver the fix — no baseline, not idempotent, never reaches prompts or skills: fix both at source and prove an already-migrated client is remediated in place**
Type: bug — client-install fidelity + update-path remediation (client-shipped surfaces; reported from a completed real-client v11 migration).
Status: Open
Target: v11.0
Blockers: None. Every defect is reported with file:line evidence and reproduced from a real client install; the remediation machinery (`init-project.sh --update` + customization-preserve) already exists and needs measurement, not invention.
Unblocks: the public launch — a fresh v11 install that passes its own shipped gate, and an already-migrated client that can take the fix via `--update` without re-migrating or converting pack-owned files into customized ones.
File/Symbol: `project-template/docs/pack/METHODOLOGY.md`; `project-template/docs/pack/INSTALL-PROCEDURES.md`; `project-template/docs/pack/prompts/pm-chat.md`; `project-template/.claude/agents/auditor-architecture.md` + `auditor-ops.md` and their `.codex/agents/*.toml` + `.agents-plugin/` counterparts; `scripts/migrate-v10-to-v11.sh` (the S5 install stage); the client install map in `scripts/init-project.sh` + `scripts/lib/validate_checks/` (the two grouping prompts absent from it); `scripts/lib/customization-preserve.sh` + `scripts/lib/three-way.sh` + `scripts/init-project.sh` `cmd_update` (the remediation path); `project-template/scripts/.docs-gate-allowlist.txt` — docs-researcher census completes the set.
Description:
  A real client completed a full, correct v10→v11 migration (accounting gate PASS on all three streams, Gate 2 PASS, all 72 triage items discharged) and then found `bash scripts/validate-docs.sh` failing with **25 violations, every one of them originating in unmodified pack-shipped files**. A fresh v11 install reproduces them identically. The client cannot remedy them without converting pack-owned files into customized ones, which would then sidecar on every future update — so the fix must land at source.
  **The reported families.** (a) Two of seven auditor agent definitions reference the audit-methodology skill by a bare `skills/…` path where the other five use the skill name alone — an internal inconsistency across three CLI trees, six files. (b) Thirteen client-installed doc references point at pack-repo-only paths that are never installed into a client, including one prose example the gate cannot distinguish from a real reference. (c) One reference to the `.gemini/` tree that v11's own migration retires. (d) Two pack docs trip the pack's own deferred-vocabulary axis in legitimate prose. (e) The deferred axis matches inside a backticked FILE PATH in a client RAG-manifest row — client-unfixable by rewording, since only renaming a locked planning artifact would clear it; the gate should not scan link targets and backticked paths as prose. (f) Five v11 docs that ship in `project-template/docs/pack/` were not installed by the migration, producing six further dangling references and two skills with no spec behind them. (g) The shipped allowlist's own policy forbids widening for borderline hits, yet the shipped allowlist does not cover the pack's own findings — so a correct install can only pass by violating the policy; fixing (a)–(f) at source dissolves this rather than widening anything.
  **Two corrections measured pack-side, not in the report.** The bare-path fix is to match the other five agents' form (skill NAME, no path), not to correct a path. And family (f) is TWO defects, not one: three of the five docs ARE in the client install map — so the map says install and the migrator did not, a migrator-vs-map divergence whose blast radius must be measured across every mapped file — while the two grouping prompts are genuinely absent from the map.
  **The update path is broken at its root, and this entry owns it.** Measured at pack HEAD and reproduced by running the tool: `cmd_update` passes an EMPTY BASE to `customization_preserve` at every call site, documented in its own comment ("BASE is left empty (no prior pack baseline available offline…)"). With no BASE, `three_way_classify` takes the `base absent, ours present, theirs present` branch and returns `project-shadows-new-pack` **unconditionally — it never compares OURS to THEIRS**, contradicting its own header contract, which says that disposition should classify by ours-vs-theirs and let the caller route if they differ. An untouched file and a heavily customized file are indistinguishable to it. Three measured consequences: (1) NOT IDEMPOTENT — a second `--update` against an UNCHANGED pack produced 105 of 110 files classified needs-reconciliation with 105 sidecars written, including a file proven byte-identical by `cmp -s`, so a client who runs the supported update command twice must hand-resolve its entire tree; (2) COVERAGE GAPS — the update file-set reaches ZERO files under `docs/pack/prompts/` and the skills trees, and a simulated prompt-side fix did not land while doc and agent fixes did; (3) the failure is arrival-path-independent, so every client on every future release is affected, not only those that arrived by migration. Shipping a release whose own update command cannot be run twice safely is a worse client experience than the defects that surfaced it.
  **The remediation path is in scope and is a deliverable, not a side effect.** Already-migrated clients must be able to take these fixes via `init-project.sh --update` with no re-migration. Most pack-owned fixes should classify `pack-update-applied` (silent replacement) precisely because a disciplined client leaves pack-owned files pristine. Three things need measurement rather than assumption: (1) where the three-way BASE comes from for a client that arrived by MIGRATION rather than fresh install — if that baseline is absent or unreliable, files degrade toward looking customized and the whole clean-update premise fails, so this is measured FIRST; (2) a client who already worked around family (f) by hand-copying the missing docs now holds files with no pack baseline, classifying `project-shadows-new-pack` rather than a clean install — the sensible workaround must not be punished with sidecars; (3) whether `--update` reaches every surface these fixes touch (agent definitions across three CLI trees, prompts, docs).
Acceptance criteria: `bash scripts/validate-docs.sh` exits 0 on a freshly-installed v11 client tree with zero allowlist additions for pack-owned references; the deferred axis no longer matches inside backticked paths or link targets, proven by a mutation test on the reported client-unfixable case; every path the install map declares is installed and CURRENT — after the run the destination exists and its bytes are byte-identical to the pack source the map declares for it, and the only departures admitted are the two the run itself attributes, in the disposition report that run writes: a DIVERGENT destination whose row for that path carries disposition `merged-with-customization` or `customization-detected-needs-reconciliation` (a client customization the run preserved), and an ABSENT destination whose row carries `project-deleted-pack-kept` (a client deletion the run honored); the row alone attributes it — no sidecar, diff, or marker region is required, and none may be demanded; every other end state is STALE and FAILS, including a divergence or absence with no row of the matching kind for that path and any row whose disposition falls outside those two sets, so a path the run could not classify is never exempt and a v10-byte or missing installed copy still fails — by BOTH the fresh-install and migration paths, with the map/migrator divergence measured across all mapped files and closed; the two grouping prompts are in the map and installed; **and the update-path remediation is PROVEN, not asserted — on a scratch clone of an already-migrated client tree, `init-project.sh --update` with the fixed pack ends with the doc gate green, NO sidecar that differs from its live file (the gate's own `cmp` predicate — "zero new sidecars" is unsatisfiable by construction for a client who deleted a top-level key the pack still edits, since that file is re-dispatched every run and the merge honours the removal, so each re-created sidecar is a byte-copy of the unchanged live file), ZERO files the client customized touched, and no re-migration**, including the case where the client had already hand-copied the missing docs; `three_way_classify` honors its own documented contract — with BASE absent it compares OURS to THEIRS and distinguishes identical from divergent, proven by a unit test that BITES on the pre-fix behavior; `--update` is IDEMPOTENT, proven by running it twice against an unchanged pack on a real-shaped client tree and observing no sidecar that differs from its live file and zero reconciliation findings on the second run; a genuinely customized file still routes to reconciliation, proven by a test in the opposite direction so the fix cannot silently overwrite client work; the update file-set reaches every client-installed surface, with the covered set derived from the install map rather than a hand list, and prompts + skills coverage each proven by a simulated fix landing; the classifier's header contract and the `cmd_update` comment are reconciled to the shipped behavior; full CI battery green.
