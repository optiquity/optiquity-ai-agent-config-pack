Description:
  **Problem:** The pack codifies universal agent discipline in ONE loadable skill (`commit-discipline`) that every pack agent loads — one home, consistent across all roles, no per-def duplication. The project side homes the same discipline differently: spread across `PM-CHAT.md` permission profiles + each agent def. This asymmetry surfaced during BD-226's F-9 analysis. The question this BD investigates: should the project gain a `commit-discipline`-style universal-discipline skill (single home, loaded by all project agents, mirroring the pack), or is the current `PM-CHAT.md` + per-agent-def home the correct project-side design?
  **Context / non-goals (from the BD-226 F-9 analysis):** The pack's TWO-skill split (`commit-discipline` = universal, loaded by all 5 agents; `implementation-report` = coder-only) is itself JUSTIFIED by distinct loading (merging would force the 4 RO agents to carry the coder's report spec) and is NOT in scope to change. This BD is ONLY about the project-side home for universal discipline. The BD-226 F-9 fix (decouple "regime = where you write" from "patch = RW-only, post-review-clean") lands in the existing surfaces regardless of this BD's outcome and does not wait on it.
  **Trade-offs to weigh:** (a) a shared project skill reduces per-def duplication + drift risk and gives every project agent one consistent discipline source (the pack's rationale); (b) the current home keeps discipline in the orchestrator/permission-profile surface the project already uses and avoids adding another client-shipped skill (more files to install/maintain). The investigation must measure the ACTUAL duplication across the project agent defs and the project skill-loading mechanism (`PLATFORM-SKILLS.md` matrix / Tier-0) before recommending.
  **Solution:** an architect investigation evaluates the two options with evidence (measured duplication across the project agent defs, the loading mechanism, drift risk, install/maintenance cost), and the user records a decision. No code change in this BD itself — it is a design-decision BD. If "add a project skill" is chosen, a follow-on implementation is scoped (planner → coder) under this BD or a successor.
Acceptance criteria: an architect design doc evaluates status-quo vs new-shared-skill with measured evidence (per-def duplication count, loading mechanism, drift/maintenance cost) and a clear recommendation; a user decision is recorded; if "add a skill" is chosen, the implementation scope (which agents load it, install wiring, the `skill-agent-maintenance-mechanical` escalation path) is defined.
