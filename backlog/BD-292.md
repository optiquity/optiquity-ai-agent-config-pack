**BD-292 — Migration harness diagnostics: a failed sandbox run destroys its own evidence, and Gate 2's validate-pack leg couples the client's migration outcome to the pack tree's state**
Type: bug — migration harness + migrator gate (pack-dev tooling; both defects measured live during the BD-291 acceptance).
Status: Open
Target: v11.0
Blockers: None. Both defects are measured and reproducible; neither is on the client-shipped surface.
Unblocks: a failed migration run that can be diagnosed from its own output, and a Gate-2 verdict that reflects the client's tree rather than the pack developer's working state.
File/Symbol: `scripts/dry-run-migration.sh` (the `dry_cleanup` EXIT trap and the results dir it removes); `scripts/lib/migrator-stages.sh` and/or `scripts/lib/checkpoint.sh` (the Gate 2 `validate-pack` verification leg); `pack-ops/DRY-RUN-MIGRATION.md` (§ Recovery); `scripts/tests/fixture-dependent/test-dry-run-migration.sh` (regression coverage) — architect confirms the set.
Description:
  Both defects surfaced during the BD-291 run-(ii) acceptance and were diagnosed by manual reproduction; neither affects the shipped client deliverables.
  **D-A — the harness destroys its own diagnostics on failure.** `dry_cleanup` removes the work dir on EVERY exit path, including a red one. The results dir it deletes holds the adapter's `apply-stderr.log` / `resume-stderr.log` — the only record of WHY a run failed. Measured: an `--apply-sandbox` run exited 7 naming `resume-stderr.log` as the diagnostic, and that file was already gone when the message was read; the cause was recoverable only by re-cloning and re-running the whole sequence by hand. The pack already holds the correct principle elsewhere — a failed commit KEEPS its worktree as the recovery fallback — and the harness's own recovery prose points at paths its trap has removed. Direction: preserve the results dir (or copy it beside the `--report-out` target) on a non-zero exit, keep the clean-on-success behavior, and make the recovery prose name a path that still exists.
  **D-B — Gate 2's validate-pack leg reads the pack tree, not the migrated tree.** The migrator's post-Phase-A Gate 2 runs the pack's `scripts/validate-pack.py`, whose subject is the pack repository. Measured: a migration on a clean, correct client clone failed Gate 2 with `[FAIL] validate-pack: validator exited 1` solely because an orchestrator-owned file in the pack checkout exceeded a size cap — a condition with no relationship to the client's migration. For a client running an installed pack the leg is usually inert, which is precisely why the coupling can sit unnoticed; when it does fire it produces a false red on a correct migration, and Gate-2 failures are documented as non-resumable (restore-from-backup and start over). Direction: decide whether the leg belongs in a client-facing gate at all — and if it stays, scope it to what the migration actually produced, so the verdict cannot depend on the state of a tree the client does not own.
Acceptance criteria: a failing `--apply-sandbox` run leaves its adapter logs readable at a path its own error message names, proven by a test that forces a failure and asserts the evidence survives; Gate 2's verdict is independent of the pack checkout's working state, proven by a test that dirties the pack tree in a way that previously reddened the gate and shows the migration still passing; the harness recovery documentation names only paths that exist post-failure; full CI battery green.
References: measured during the BD-291 Wave-D acceptance — the false-red Gate 2 reproduction and the destroyed-evidence sequence are described in this entry; BD-291's preserved plan (`maintenance-docs/v11-implementation/PLAN-BD-291.md` § Wave D) carries the acceptance procedure both defects were found in.
Position: v11.0 by the standing no-deferral rule — pack-dev tooling, not on the client-shipped surface and not a launch dependency; retarget to v11.1 is a one-word user decision.
