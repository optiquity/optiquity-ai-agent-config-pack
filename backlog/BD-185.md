Description: Pack-side design work to address four problems framing the BD:

  **P1.** Mid-work phase splits have no first-class tracker representation. METHODOLOGY.md §339-366 defines "Part 1, Part 2" sub-sections inside IMPLEMENTATION-PLAN.md, but the tracker form-family (`.github/ISSUE_TEMPLATE/work-item.yml`) has no Part field, no part:M label, and computes task titles as `Phase N.M` with no part awareness.

  **P2.** The hierarchy changes when parts are added. Pre-mitigation: Phase N → Tasks N.1..N.k. Post-mitigation: Phase N → Parts (1..p), each part containing its own tasks. Existing task IDs (N.1..N.k) must survive this transition without renumbering. Current v11 design has no documented mechanism for grouping existing tasks under parts.

  **P3 (TRACKER — moved to BD-216).** Tracker-mode execution ordering has no native mechanism. GH Issues lack a user-mutable execution-order field. Issue numbers reflect creation order. Blockers/dependencies give only partial order. Sub-issues give containment, not sibling order. In flat-file mode, ordering lives in IMPLEMENTATION-PLAN.md as "execution notes" (METHODOLOGY:335). In tracker mode, IMPLEMENTATION-PLAN.md is a regenerated mirror — execution notes do not survive sync. This tracker-native-ordering problem is carried by BD-216 (deferred, no version); this entry's flat-file half owns only the flat-file execution-notes ordering.

  **P4 (flat-file half here; tracker half in BD-216).** v10→v11 migration must handle pre-existing whole-number phases without manual intervention (flat-file pass-through). The flat→tracker ordering-init leg moves to BD-216. All v10.x and v11 projects already have whole-number-only phases; the flat-file solution must absorb that state cleanly.

  **Goal (flat-file half, re-scoped 2026-06-13):** Flat-file mode can express phase splits at creation, mid-work phase-to-parts expansion, and explicit flat-file execution ordering — all without renumbering existing phase or task IDs and without STATUS.md serving as the ordering SSOT. The phase-parts structure is deterministically serializable (one canonical machine-parseable form). The TRACKER counterpart of this goal (express the same in tracker mode without flat-file artifacts as SSOT) is BD-216.

  **Success Criteria (flat-file half — this entry):**
  - SC1. Phases that grow too large at creation time can be split into multiple phases (each with a new immutable number), in flat-file mode.
  - SC2. Phases that grow too large mid-work can be expanded into multi-part form (Phase N → Part 1..p, each part containing tasks), preserving the existing phase number and all existing task IDs, in flat-file mode.
  - SC3. Phase numbers and task IDs (N.M) are never renumbered. This invariant holds across all flat-file operations defined by this BD.
  - SC4 (flat-file leg). Execution ordering of phases is expressible in flat-file mode via execution notes, and is deterministically serializable. *(The tracker leg of SC4 — ordering that does NOT depend on any flat-file artifact and does NOT use GH Projects as a single-phase ordering substitute — moves to BD-216.)*
  - SC5. STATUS.md remains a dashboard. Its role does not expand to ordering SSOT.
  - SC8 (flat-file leg). The v10→v11 migrator passes pre-existing whole-number phases through unchanged (whole-number pass-through). *(The tracker leg of SC8 — flat→tracker forward-migration ordering init from current implementation order — moves to BD-216.)*
  - SC-SER (NEW, US-4 hard constraint). The phase-parts structure resolves to ONE canonical machine-parseable serialization — no free-prose ambiguity, no nondeterministic ordering — so BD-215 can round-trip phase-parts.

  **Success Criteria moved to BD-216 (tracker half):** SC6 (tracker form-family `work-item.yml` Part field + part:M label namespace + template_version delta per BD-068/BD-069); SC7 (BD-060 TrackerProvider bi-directional sync of part membership + execution order across forward and reverse operations); SC4-tracker + SC8-tracker (above).
