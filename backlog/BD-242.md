**BD-242 — Adopt semantic versioning + Apple-style release qualifiers for the pack: `vMAJOR.MINOR.PATCH (RCn | GA[n])` (replace the two-level `vN.M` scheme)**

Replace the current two-level `vN.M` (major.minor) scheme with three-level semantic versioning `vMAJOR.MINOR.PATCH` + an Apple-style parenthetical release qualifier (the release state). Researcher (version-format surface census) → architect → planner → coder; LARGE under the BD-238 standard (structural, cross-surface, trinity + validate-pack) ⇒ full pipeline with adversarial passes.

Decisions (user 2026-06-20):
  - **Number format: standard semver, unpadded integers** — `vMAJOR.MINOR.PATCH`, e.g. `v11.0.1` (NOT zero-padded fixed-width).
  - **Release qualifier: Apple-style parenthetical** = the release STATE — `v11.0.0 (RC1)`, `(RC2)`, … `(RCn)` → `(GA)`, and rarely `(GA1)`/`(GA2)` when a shipped GA needs a re-release for issues. The parenthetical is the human/README/changelog DISPLAY form.
  - **State = the qualifier** — the release state IS the RC/GA qualifier attached to the number; no separate lifecycle field.

Description:
  **Problem:** the pack's two-level `vN.M` scheme has no patch level (can't express a bugfix-only release) and no release-state qualifier (can't express release-candidate vs general-availability). That is coarser than needed for clean development, launch, and distribution.
  **Goal:** adopt `vMAJOR.MINOR.PATCH` (unpadded semver) + an Apple-style parenthetical qualifier that IS the release state — `v11.0.0 (RC1)` … `(GA)` / rarely `(GA1)`/`(GA2)` — consistently across every version-format surface, with a tag-safe encoding for git (tags cannot contain spaces).
  **Architect-designed (measure-then-bound — the user's decisions above are FIXED inputs; these are the open design points):**
    1. **Tag-safe encoding** of the parenthetical display form (git tags can't contain spaces — e.g. display `v11.0.0 (RC1)` ↔ tag `v11.0.0-rc1`; display `(GA)` ↔ tag `v11.0.0` or `v11.0.0-ga`). Define the display↔tag bijection.
    2. **Bump rules for a config-pack context** — what counts as MAJOR (breaking; e.g. migration-requiring) vs MINOR (backward-compatible feature/template) vs PATCH (fix), concrete not vibe.
    3. **GA1/GA2 vs patch bump** — when a post-GA fix becomes `(GA1)`/`(GA2)` vs a `v11.0.1` patch.
    4. **Reconcile the existing "bare major tag floats to latest minor" + tag-move sequence** with the new three-level + qualifier scheme.
    5. **Changelog granularity** — keep one `vN.md` per MAJOR (point releases inside), or finer?
    6. **`validate-pack` version-token regex** + the `MIGRATION-vN-to-vM.md` convention update.
    7. **Migration of the current `v11.0` → `v11.0.0`** and the v11.0 LAUNCH path (RC→GA) IF v11.0 launches under the new scheme (the Target/BD-093 sequencing decision).
  **Process:** `pack-docs-researcher` (exhaustive census of EVERY surface that encodes/parses/displays/sorts a version) → `pack-architect` → `pack-planner` → `pack-coder`, under the BD-238 large-BD standard (adversarial passes; structural/trinity/validate-pack scope).
Acceptance criteria: the pack uses `vMAJOR.MINOR.PATCH (RCn | GA[n])` (unpadded semver + Apple-style parenthetical qualifier = the release state) with a defined display↔tag-safe bijection; the trinity Versioning rules ×3 + README table + changelog scheme + tag convention + migration-script naming + `validate-pack` version regex + `init-project.sh` stamping are all updated consistently (no surface left on the old `vN.M` scheme); the major/minor/patch bump rules + GA1/GA2 semantics are concretely defined; the current `v11.0` → `v11.0.0` migration + the v11.0 launch path are specified; `validate-pack` green; no broken version cross-references; researcher-then-architect-designed (not Pack-Chat-authored).
