Description:
  **Problem:** the pack's two-level `vN.M` scheme has no patch level (can't express a bugfix-only release) and no release-state qualifier (can't express alpha / beta / release-candidate / general-availability). That is coarser than needed for clean development, launch, and distribution.
  **Goal:** adopt the locked scheme below — `vMAJOR.MINOR[.PATCH]` (unpadded integers) plus a release-state qualifier — consistently across every version-format surface, applied forward-only.
  **The locked scheme (the authoritative, current scheme):**
    - **Number:** `vMAJOR.MINOR[.PATCH]` — unpadded integers. MAJOR and MINOR are ALWAYS present; PATCH is OMITTED when zero (`v11.0`, never `v11.0.0`).
    - **Qualifier (the release state):** one of `alpha`, `beta`, `RC1`…`RCn`, `GA`. Only `RC` is numbered (unpadded, from 1: `RC1`, `RC2`, …); `alpha`, `beta`, and `GA` are NEVER numbered. Casing: `alpha`/`beta` are lowercase words; `RC` and `GA` are uppercase — casing is identical in display and in tags (there is NO lowercased tag variant). A qualifier applies ONLY to a `MAJOR.MINOR` version; a PATCH is NEVER qualified (a patch is always plain `vMAJOR.MINOR.PATCH`).
    - **Display ↔ git-tag:** the DISPLAY form shows the qualifier parenthetically — `vMAJOR.MINOR (RC1)`. The git TAG is the display with ` (X)` rewritten to `-X`, case preserved: `v11.0-alpha`, `v11.0-beta`, `v11.0-RC1`, `v11.0-GA`. Qualifiers MAY appear in tags. The `-X` (rather than ` (X)`) encoding exists ONLY because git refs cannot contain spaces or parentheses.
    - **GA is transient:** `(GA)` is displayed ONLY briefly pre-launch — a window where docs + code are FROZEN — to broadcast an imminent release and that public feedback is welcome (feedback may land in a later patch or minor). AT LAUNCH the `(GA)` qualifier is DROPPED → the released steady-state version is the BARE number (`v11.0`), with no qualifier ever after.
    - **State progression:** `alpha → beta → RC(n) → GA → launch (bare)`. Every state transition AND every git tag is the USER's manual decision — there is NO heuristic and NO automation. The pack's tooling only READS / DISPLAYS / VALIDATES the version string that exists; it never decides when to tag or which tag to select.
    - **Forward-only:** v1–v10 and existing v11 references are LOCKED (not renamed); the new scheme applies going forward only. All parsers/validators MUST continue to accept the old two-level `vN.M` form alongside the new form.
  **Scope (the surfaces the implementation updates — this entry names them; it does NOT implement them):**
    - Trinity Versioning rule (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`).
    - `README.md` versioning-convention prose + the going-forward Version History table format.
    - `validate-pack.py` version-token regex — accept old `vN.M` AND new `vMAJOR.MINOR[.PATCH]` plus an optional qualifier suffix `-(?:alpha|beta|RC\d+|GA)`; preserve MAJOR extraction + changelog resolution; plus its tests.
    - `changelog/` — per-major granularity kept; the going-forward H3 may carry the qualifier label.
    - `scripts/lib/detect.sh` `detect_pack_version` — continues to pass the git tag through verbatim (no new logic; a stale comment updated).
  **Out of scope / forbidden:** any tagging automation or heuristics — no precedence ladders, no multi-tag selection logic, no "GA window" timing rules, no floating-tag lifecycle prescriptions, no lowercasing of qualifiers. The tooling reads/displays/validates only; the user decides every transition and tag.
  **Process:** the versioning scheme is user-LOCKED (the design decision is settled, not pending an architect), so the remaining cross-codebase work is a LEAN, mechanical encoding of the locked scheme across the named surfaces — `pack-planner` → `pack-coder`. The BD-238 large-BD standard (structural/trinity/validate-pack scope) remains applicable, but its adversarial passes are at the user's ELECTION here rather than mandated, since the design is already locked. This entry is a single-file scheme lock; the cross-codebase implementation is the later step.
