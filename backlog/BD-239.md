Description:
  **Problem:** the project (client) side has no codified large-phase development-pipeline standard — its process docs cover the base workflow + the project agents, but not the rigorous adversarial-review + reconciliation + parallel-worktree pipeline. A client developer running a large phase has no official standard to follow.
  **Goal:** codify, for the project side, the SAME pipeline as the pack-side companion standard (entry #238), re-applied to the project's PHASE-based lifecycle + the project's own agents — as the DEFAULT STANDARD for LARGE PHASES, with the two adversarial reviews + reconciliation OPTIONAL (user-elective) for SMALLER PHASES.
  **Vocabulary (project terms only — no pack work-item concepts in the shipped standard):** the project's development workflows are organized around PHASES (and phase tasks), NOT around backlog items. TD entries are the project's tech-debt backlog; the pipeline + the size-tiering are PHASE-based, never TD-based. This standard is documented in project-side surfaces and uses ONLY project vocabulary (phases, phase tasks, TD backlog, groupings, the project agents).
  **The standard (full flow, with options — same agent ordering as the pack-side companion, project-audience):**
    1. **Optional researcher set — FIRST step, before the first architect.** Zero, one, or both of: an **INTERNAL** researcher (the project's codebase/docs inventory + blast-radius census) and an **EXTERNAL** researcher (CLI / tool / framework / API docs verification against authoritative sources). "May be needed" — invoked per the phase; optional-by-need at ANY size.
    2. **Architect** → design, including the REQUIRED parallel/dependency map (which phase tasks/commits run in parallel isolated worktrees vs serial).
    3. **Adversarial architect review** (fresh, clean-context instance) → PM-chat triage of findings → **[reconciliation architect — only if the review returns NEEDS-REWORK]**; loop until READY.
    4. **User design review** (the design gate).
    5. **Planner** → implementation-ready plan, including its OWN parallel/dependency map.
    6. **Adversarial planner review** (fresh instance) → triage → **[reconciliation planner — only if NEEDS-REWORK]**.
    7. **User planner-to-coder gate.**
    8. **Parallel worktree coder waves** — scheduled off the parallel/dependency map: disjoint-file phase tasks run as concurrent coders, each in its own isolated worktree; same-file ⇒ serialize. Each commit's bounded review/fix cycle (≤2 review/fix pairs + 1 final) runs IN its worktree; the patch is produced only after review-clean; patches apply to the canonical tree SEQUENTIALLY (atomic per patch) with the conflict protocol (STOP + re-spawn fresh, never hand-merge); commits land with user approval. Superseded design/plan docs are DELETED as the pipeline iterates (anti-contamination); the audit set is preserved into the project's implementation-record area.
    The two adversarial passes are the MINIMUM for a large phase; ADDITIONAL architect/planner rounds are added when larger gaps are found.
  **Size-tiering (project uses PHASES):** **LARGE PHASE** = the full pipeline by default (the two adversarial reviews + reconciliation as the minimum). **SMALL PHASE** = the base flow (optional researcher → architect → planner → coder + the bounded review/fix cycle) with the two adversarial reviews + reconciliation OPTIONAL at user election. The architect defines the large-vs-small-phase criterion measure-then-bound (e.g. cross-surface / blast-radius / structural — concrete, not a vibe).
  **Where it lives:** the project-side SSOT surfaces — `project-template/docs/pack/METHODOLOGY.md` + `project-template/docs/pack/PM-CHAT.md` + the project trinity Project-memory + the project agents' docs as the architect designs. The standard SHIPS to client projects, so it must use only project vocabulary (no pack work-item references leak into the shipped deliverables).
  **Process:** architect-first (touches the project process docs + trinity) → planner → coder, run per the pack-side companion standard's pipeline (this entry re-applies that established standard to the project surface).
Acceptance criteria: the project-side large-PHASE pipeline is documented as ONE official, size-tiered standard (the full chain incl. the optional internal/external/both researcher first step + the large/small-PHASE criterion + adversarial-as-minimum-for-large / optional-for-small + reconciliation rounds + parallel-worktree coder waves); it lives in the project-side SSOT surfaces (METHODOLOGY.md / PM-CHAT.md / project trinity) and ships to clients; it uses ONLY project vocabulary (phases, phase tasks, TD backlog, groupings, project agents) with NO pack work-item references leaking into the project deliverables; it is consistent with the pack-side companion standard's pipeline shape; `validate-pack` green; architect-designed (not PM-chat-authored).
