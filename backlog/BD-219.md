**BD-219 — CI runtime optimization: tests-job matrix-sharding + `validate-pack --only-check` (effectiveness-preserving)**
Type: feat — CI/test-infra performance. Cut the `Validate Pack` workflow wall-time WITHOUT reducing test coverage or effectiveness. Full pipeline: architect (CI/perf design + the `--only-check` contract) → planner → coder → bounded review/fix.
Status: Open
Target: v11.0.
Blockers: None technical (independent of BD-197 content). SEQUENCING ONLY: the user directed this run DIRECTLY AFTER BD-197 is Resolved (2026-06-14) — i.e., ahead of the other remaining v11.0 work (BD-185/206/205/etc.). Do not start until BD-197 is Resolved.
Unblocks: faster per-push CI feedback for all pack development (the battery currently dominates iteration time), with zero loss of coverage.
Problem: The `Validate Pack` workflow's `tests` job is the wall-time long pole (~6–7.5 min/run as of 2026-06-14, e.g. C6a `4226dc8` = 7m25s). Measured drivers (HEAD ~`4226dc8`): the `validate` and `tests` jobs already run in PARALLEL (separate runners, no `needs:`), so wall-time = the `tests` job; the `tests` job runs ~67 scripts SEQUENTIALLY in one runner (no `strategy: matrix`/sharding); and **238 `validate-pack.py` invocations** occur across the battery (26 per-check tests + others each spawn the FULL validator, which re-scans the whole tree for ALL ~56 checks even when the test targets ONE check). `validate-pack.py` has NO single-check mode. This is the `ci-check-runtime-compounding` pattern at the battery level.
Scope (two effectiveness-PRESERVING levers — every test still runs, every assertion preserved):
  (1) **Matrix-shard the `tests` job** — split the ~67 wired scripts across N parallel runners via GitHub Actions `strategy: matrix` (a stable sharding scheme, e.g. by script-name hash or an explicit shard map). Wall-time drops ≈ linearly (4 shards → ≈ tests-job-time ÷4 minus per-shard setup). NO change to what is tested. The architect designs the shard count + balance + how the shard list stays in sync as scripts are added (a wiring-completeness guard so a new test can't silently fall out of all shards — measure-then-bound).
  (2) **Add a `--only-check <N>` (and/or `--only-check NAME`) mode to `validate-pack.py`** so the per-check tests run ONLY their target check instead of all ~56. Each of the 238 invocations then does ~1/56th the work. EFFECTIVENESS-PRESERVING: the per-check test still asserts its check against the same fixtures; the `validate` job still runs the FULL check set (`validate-pack.py` with no flag = all checks) so nothing is skipped in aggregate. The architect specifies the exact flag contract + that per-check tests adopt it without weakening their assertions.
  (3) **Minor:** cache Python/Node setup across runs if it yields a clean win (small).
Out of scope: REMOVING or weakening any check or test (effectiveness must be unchanged — this is a HARD constraint, CI-verifiable by confirming the full check set + the full wired test list are unchanged); any change to BD-197's worktree-isolation behavior; restructuring checks themselves.
Acceptance criteria: measurable `tests`-job wall-time reduction (record before/after); the COMPLETE set of checks still runs in the `validate` job (no check dropped) and the COMPLETE wired test list still runs (sharded, none silently dropped — a wiring-completeness guard proves every test lands in exactly one shard); per-check tests using `--only-check` still catch their check's regressions (mutation-proven); full CI battery green; the `ci-check-runtime-compounding` per-check runtime guards remain.
References: BD-197 (added the per-check tests 52/53/55/56 this builds on); the `ci-check-runtime-compounding` Pack-memory rule (the root-cause pattern); `.github/workflows/validate-pack.yml` (the `validate` + `tests` jobs); `scripts/validate-pack.py` (the full-tree validator gaining `--only-check`).
