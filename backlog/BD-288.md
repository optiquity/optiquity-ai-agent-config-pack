Description:
  **Problem — two distinct defects on one family of checks.**

  **(1) The BARENESS axis has a walk-scope hole.** Two checks gate cross-references for *bareness* (a filename reference carrying no directory qualifier): Check 40 walks `pack-ops/*.md` — a NON-RECURSIVE glob, 11 files — and Check 43 walks `_iter_client_installed_files()` = `project-template/**` plus only those `supporting-docs/` entries listed in `scripts/init-project.sh`'s `_CLIENT_INSTALLED_FILES` block (`_SANCTIONED_PACK_SIDE_SHIPPED` is frozen empty). Measured at HEAD: exactly 2 of the 10 `supporting-docs/` files are client-installed (`METHODOLOGY.md`, `INSTALL-PROCEDURES.md`), so the other 8 are walked by NEITHER bareness check. The hole is wider than `supporting-docs/`: the repo-root `README.md`, the pack-root trinity (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`), and the ~150-file per-CLI operating-doc set (`.claude/` + `.codex/` + `.agents/` agent and skill definitions) are ALSO walked by neither.

  **(2) The EXISTENCE axis is broad but blind to stale-but-resolvable paths.** Check 68 (`_CHECK_68_INCLUDE_TREES = ("project-template", "supporting-docs")` + `README.md` + the 158-doc operating-doc IN set, which DOES include the pack-root trinity) covers nearly the whole bareness hole — but only for *existence*. Its resolution is: a qualified path resolves if the path exists, ELSE if `Path(token).name in index` — a BASENAME-INDEX FALLBACK. So a qualified path that is wrong but whose basename exists somewhere in the tree resolves clean, and a bare basename resolves clean whenever the basename exists anywhere. Check 68 therefore cannot see a reference that points at a file which MOVED. The identical fallback is present in the client twin `project-template/scripts/validate-docs.sh` (`if norm in relpaths or base in basenames: continue`), so the client gate carries the same blindness.

  **(3) Check 81's active-BD matcher has never fired — same class, different surface (folded in at BD-open by user direction).** Check 81 (`check_open_bd_structured_surface_field`) gates that every BD in active design carries a structured `File/Symbol` path list, and its trigger is membership in `pack-ops/session-state.json` `active[]`. But `_check_81_active_bd_ids()` accepts a member ONLY when it is a DICT carrying a `bd` key matching `^BD-\d+$`; a plain-string member is silently skipped. Measured across the snapshot's entire committed history, EVERY `active[]` value has been a list of plain strings (`["BD-093"]`, `["BD-287"]`, `["BD-205"]`, ...). The FAIL leg has therefore never fired once since the check was authored — it registers, prints OK, and gates nothing.
  **The data shape is correct; the matcher is the defect.** Two consumers of the same field disagree, and the string form is the load-bearing one: `scripts/dashboard-render.py` does `" ".join(session.get("active", []) or [])`, which raises on dict members, and the user-owned verbatim spec `pack-ops/DASHBOARD-SPEC-PACK.md` states explicitly that `active[]` may hold long descriptive strings. So the fix direction is NOT to migrate the data to dicts on the check's say-so; the architect decides, with the renderer and the spec as binding constraints. Check 82 consumes an adjacent trigger and must be re-verified for the same inertness.
  **Why it belongs here and not in a new entry.** This is the SAME defect class as (2): a records-style check that stays green because its matcher never reaches the reality it claims to verify (`declare-verify-backing`). BD-288's remit is that class, not one check family.

  **Why this is not theoretical — the mechanism, verified in code.** `supporting-docs/MIGRATION-v10-to-v11.md` carried 12 BARE `MERGE-STRATEGY.md` references after that file moved to `pack-ops/MERGE-STRATEGY.md`. Check 68 resolved all 12 (the basename existed) and stayed green; Check 40 never walked the file because it is not client-installed; Check 43 never walked it for the same reason. The references survived undetected until a reviewer found them by hand during the release cut, and were qualified to `pack-ops/MERGE-STRATEGY.md` in the RC1 cut commit. Both halves of the mechanism are confirmed against the check bodies at HEAD.

  **Measured exposure (the measure-then-bound census input, run with Check 40's own extraction + allowlist + anchor-phrase + same-dir rules).** Raw occurrence counts on the live uncovered surfaces, classified by candidate-set size, NOT yet triaged KEEP-vs-STRIP: the 8 non-installed `supporting-docs/` files — 18 zero-candidate / 43 single-candidate / 7 multi-candidate; the 6 repo-root markdown files (README + trinity) — 11 / 26 / 5; the 65 per-CLI operating-doc files (`.claude/`, `.codex/`, `.agents/`, `.agents-plugin/`) — 0 / 31 / 4. Roughly 145 occurrences on live surfaces requiring individual KEEP-or-STRIP classification. A large share are legitimate KEEPs — e.g. the trinity's bare `BACKLOG.md` / `IMPLEMENTATION-PLAN.md` / `CHANGELOG.md` describe a CLIENT-side artifact with no pack-repo file, and `SKILL.md` has ~100 candidates by ecosystem convention (the `filename-uniqueness-heuristic` structural-collision exemption). Every zero-candidate reference measured in the 8 `supporting-docs/` files is ALREADY on `pack-ops/.dangling-ref-allowlist.txt` as an intentional KEEP, which is why the existence axis is green: the uncovered axis is BARENESS, not non-existence.

  - **Scope grows into THIS entry, never into a new one.** Anything the architect, planner, coder, or reviewer surfaces during BD-288 is folded into BD-288 and done now.   - **Design questions left to the architect (not pre-decided):** whether the fix is a widened Check-40 walk, a new check, or a generalization of Check 68; whether the Check-68 basename-fallback hardening lands in this BD (it touches currently-green surfaces — `project-template/` and `pack-ops/` — and drags the client twin along under mirror-but-customize); how a fourth walk over ~150 additional files is kept cheap under `ci-check-runtime-compounding`.
