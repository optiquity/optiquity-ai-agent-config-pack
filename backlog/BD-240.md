Description:
  **Problem:** the `graph-first-context` rule opens correctly ("prefer the graph for orientation / relationship / blast-radius ... BEFORE broad tree reads") but its grep/Read fall-throughs ("exact-string / token search", "whole-file exact content") let an agent route the WHOLE discovery/recall phase to grep — bounding recall to its a-priori query patterns — and skip the graph (whose strength is "find ALL surfaces related to X"). This is worst for the docs-researcher role, whose entire value is recall over internal docs. Evidence: the BD-206 researcher ran zero graph queries, citing exactly these clauses.
  **Root cause:** the rule conflates two phases and lets the second veto the first — (a) DISCOVERY/RECALL ("what are ALL the surfaces that relate to X?" — the graph's strength) and (b) VERIFICATION/PRECISION ("the exact bytes + counts at this surface" — grep/Read's strength). The correct model is graph-first for discovery, THEN grep/Read to verify; the current wording permits "if you'll eventually need exact strings, start with grep," which produces the worst recall for the highest-stakes role.
  **Goal:** re-frame so the graph is the genuine PRIMARY discovery/recall tool whenever it exists, with grep/Read as the VERIFICATION/precision layer — separate the two phases explicitly (graph-first to establish the candidate surface set; grep/Read for exact bytes + counts). Scope the fall-throughs to true precision/availability needs (exact SSOT field VALUES, uncommitted files, archive/excluded content deliberately not in the graph) so they no longer swallow discovery. Include role-specific emphasis (docs-researcher recall mandate) and DECIDE whether spawn-prompt construction must explicitly DIRECT graph use AND the Rules-Applied block must ATTEST the graph queries run for recall-heavy tasks (so an agent cannot silently skip the graph again). Propagate across trinity, preserving the Claude-only BD-226 path-injection caveat + the AGENTS/GEMINI worktree note unchanged.
