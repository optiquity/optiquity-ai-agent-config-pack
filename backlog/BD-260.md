**BD-260 — Add the `work` earliest pre-launch release-state qualifier (before `alpha`) to the versioning scheme (BD-242 successor)**
Type: feat — STRUCTURAL pack-ops versioning-scheme extension. Extends BD-242's release-state qualifier vocabulary `{alpha, beta, RCn, GA}` with a new EARLIEST-state qualifier `work` (work-in-progress; before `alpha`), forward-only across every version-format surface. User-ratified scheme extension; a LEAN, mechanical encoding of the ratified scheme (mirrors BD-242's own process) — planner → coder, adversarial passes at the user's election.
Status: Resolved
Target: v11.0 — the honest pre-launch state for v11.0's current (pre-feature-complete) development. MUST land before BD-253's README qualifier flip (BD-253 sets the README row to the honest `v11.0 (work)` rather than overloading `alpha` — a display marker only; nothing gates on it), and before the v11.0 GA cut (BD-093, which drops the qualifier to bare).
Blockers: none on repo state. Extends BD-242 (Resolved — the versioning-scheme SSOT); the user ratifies the extended vocabulary. Sequencing: land BEFORE BD-253's README qualifier edit. COORDINATE: BD-093 (the v11.0 GA cut) reads the versioning surfaces; BD-253 consumes `work` as the honest README display qualifier (nothing mechanically keys on it).
Unblocks: an honest pre-launch state for v11.0 — removes the latent "bare `v11.0` presented as released during active development" inconsistency; lets BD-253 set the README row truthfully to `v11.0 (work)` (an honest display marker — nothing gates on it), without overloading `alpha` (dishonestly "feature-complete") or leaving the row bare (dishonestly "released").
Provenance: surfaced 2026-07-02 at BD-253's immutability design gate, under BD-253's then-planned release-state-freeze design (since superseded by BD-253's ruled immutability model — see the supersession note below). Independent of any freeze mechanism, BD-242's vocabulary had no state before `alpha`, so the only representable states for "v11.0, in development" were bare (dishonestly released) or `alpha` (dishonestly feature-complete). The architect assessment (`ASSESS-PREALPHA.md`) sized the vocabulary addition as LARGE/cross-surface (≈12 version-format surfaces, modifies BD-242's ratified scheme) → its own BD. The name `work` was chosen over `prealpha` (substring collision with `alpha`) and `prerelease` (semver umbrella-term overload — `alpha`/`beta`/`RCn` are all "prereleases") and `dev` (infra-environment collision with dev/staging/prod); `work` has no substring collision with any qualifier and no term overload.
Problem: BD-242's release-state qualifier vocabulary is `{alpha, beta, RCn, GA}` with progression `alpha → beta → RCn → GA → launch(bare)`. There is NO qualifier for a version in active development BEFORE `alpha` (not yet feature-complete). During such development the README Version cell must be a bare `vN.M`, which the versioning model defines as the LAUNCHED steady state — so a version still being built is presented as released. The README row therefore has no truthful way to express "in development" (the qualifier is an honest display marker; nothing mechanically gates on it): the only options are bare (dishonestly released) or `alpha` (dishonestly feature-complete). The vocabulary is missing its earliest state.
