**BD-260 — Add the `work` earliest pre-launch release-state qualifier (before `alpha`) to the versioning scheme (BD-242 successor)**
Type: feat — STRUCTURAL pack-ops versioning-scheme extension. Extends BD-242's release-state qualifier vocabulary `{alpha, beta, RCn, GA}` with a new EARLIEST-state, FREE/editable qualifier `work` (work-in-progress; before `alpha`), forward-only across every version-format surface. User-ratified scheme extension; a LEAN, mechanical encoding of the ratified scheme (mirrors BD-242's own process) — planner → coder, adversarial passes at the user's election.

Target: v11.0 — the honest pre-launch state for v11.0's current (pre-feature-complete) development. MUST land before BD-253 unfreezes the immutable `_rules.md` set (BD-253 sets the README row to the honest `v11.0 (work)` rather than overloading `alpha`), and before the v11.0 GA cut (BD-093).

Unblocks: an honest, editable pre-launch state for v11.0 — removes the latent "bare `v11.0` presented as released during active development" inconsistency; lets BD-253's immutability gate fix unfreeze the shipped `_rules.md` contracts truthfully (README `v11.0 (work)`), without overloading `alpha` (dishonestly "feature-complete") or leaving the row bare (dishonestly "released").
Provenance: surfaced 2026-07-02 at BD-253's immutability design gate. BD-253's fix freezes pack-shipped immutable files by RELEASE state (bare + GA frozen; alpha/beta/RCn free), read from the README version-cell qualifier. To unfreeze v11.0 honestly it needs a truthful pre-launch qualifier — but BD-242's vocabulary has no state before `alpha`, so the only representable states for "v11.0, in development" were bare (dishonestly released) or `alpha` (dishonestly feature-complete). The architect assessment (`ASSESS-PREALPHA.md`) sized the vocabulary addition as LARGE/cross-surface (≈12 version-format surfaces, modifies BD-242's ratified scheme) → its own BD. The name `work` was chosen over `prealpha` (substring collision with `alpha`) and `prerelease` (semver umbrella-term overload — `alpha`/`beta`/`RCn` are all "prereleases") and `dev` (infra-environment collision with dev/staging/prod); `work` has no substring collision with any qualifier and no term overload.
Problem: BD-242's release-state qualifier vocabulary is `{alpha, beta, RCn, GA}` with progression `alpha → beta → RCn → GA → launch(bare)`. There is NO qualifier for a version in active development BEFORE `alpha` (not yet feature-complete). During such development the README Version cell must be a bare `vN.M`, which the versioning model defines as the LAUNCHED steady state — so a version still being built is presented as released. Any mechanism that keys on the qualifier as a release-state signal (e.g. BD-253's immutability freeze) therefore has no truthful way to express "in development, editable": the only options are bare (dishonestly released) or `alpha` (dishonestly feature-complete). The vocabulary is missing its earliest state.
