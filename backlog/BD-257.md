  - `project-template/skills/<command>/SKILL.md` — the net-new AND refreshed command skills (the execution steps each command runs).
  - `project-template/scripts/` — any client-side scripts the commands invoke (execution foundation; `dependency-direction-placement` — client deliverables default project-side).

Description:
  **Problem:** the client slash-command surface (`project-template/skills/`) covers language/framework/domain skills but has gaps for common PROJECT-WORKFLOW commands a developer would want, and some existing client commands (incl. help/startup) may have drifted from the current system. BD-224 addresses the PACK-side `/pack-*` surface; this BD is its project-side analog — the client surface is a SEPARATE artifact (`pack-project-separation-of-concerns`) needing its own scoping.
  **Execution-foundation requirement (the core of this BD):** adding OR updating a client slash command is NOT merely adding/editing command text in a skill/doc/config. Each net-new command REQUIRES building its full execution foundation — the skill body (`project-template/skills/<name>/SKILL.md`) with the concrete steps it runs, PLUS any client-side scripts/actions it invokes (default home `project-template/scripts/`). A command with no working execution foundation is not shippable.
  **Existing-command refresh (IN SCOPE):** review, update, and where useful EXPAND the EXISTING client slash commands (the shipped `project-template/skills/` set, including help/startup) to reflect the current client-project state — correct stale steps/outdated references, close coverage gaps, and refresh each command's execution foundation where it drifted from the shipped scripts/flows. The shipped command surface must be accurate, not only the net-new additions.
  **Stage 1 — BRAINSTORM / DISCOVERY (decision gate; user adjudicates the set):** researcher inventories the current client command/skill surface (`project-template/skills/` + per-CLI wiring) + surveys client-workflow command patterns; architect brainstorms candidate net-new client commands AND flags existing commands needing refresh, each with the workflow it serves AND the execution foundation it needs. Pack Chat surfaces the menu; user freezes the set. NO design/impl until frozen. (Mirrors BD-224 / BD-221 Phase-0.)
  **Stage 2 — design → plan → implement** the chosen net-new commands + the existing-command refresh + their execution foundation, under the trinity rule (cross-CLI parity across the client's Claude/Codex/Antigravity surfaces per BD-221) and the skill `x-` contract (`skill-agent-maintenance-mechanical`).
  **Out of scope:** the pack-side `/pack-*` surface (BD-224 — separate artifact); the BD-221 conversion itself.
  **Hard constraints:** each new command ships its execution foundation (skill body + scripts), not just text; existing client commands (incl. help/startup) reviewed + brought current, not just net-new commands added; trinity/cross-CLI parity for every command; no boundary leak between client and pack `/pack-*` surfaces (`pack-project-separation-of-concerns`); client scripts default to `project-template/scripts/` (`dependency-direction-placement`); brainstorm set FROZEN before Stage-2; designed against the settled client surface.
  **Acceptance criteria (provisional — refined by design):** a user-adjudicated set of net-new client slash commands, each with a working execution foundation; existing client commands reviewed/updated to current state (stale steps/references corrected, execution foundation refreshed) with help/coverage expanded; cross-CLI parity; `validate-pack` green; full CI battery green; no client-install/boundary regression.
