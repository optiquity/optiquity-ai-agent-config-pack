**BD-215 — Tracker-agnostic canonical entry format: redesign + re-author all BD entries**
Type: feat — STRUCTURAL (future pack release). The format-first prerequisite for any tracker resumption.
Status: Deferred
Target: none — no release version; lands with the tracker-resumption release (the deferred cluster {BD-204, BD-207, BD-215, BD-216, BD-188, BD-212, BD-213}; BD-215 is the format-first gate the whole cluster waits on). (user 2026-06-12; cluster semantic US-5 2026-06-13.)
Blockers: BD-185 — the canonical format must round-trip phase-parts, which depends on BD-185's flat-file phase-part structure being locked and DETERMINISTICALLY SERIALIZABLE (one canonical machine-parseable serialization). No other technical blocker; deliberately deferred with the tracker work it enables. Executes BEFORE any resumption of BD-204/BD-207 (it blocks both).
Unblocks: BD-204 (pack tracker, resumption), BD-207 (project tracker, resumption).
Problem: BD-204 demonstrated that byte-faithful round-tripping of ARBITRARILY-SHAPED legacy entries through a tracker requires a fragile dual-representation design (verbatim gz64 blob + readable projection + divergence comparators + local caches), and the coherence obligations between those copies were the dominant defect source. The entries' free-form shape — inconsistent field sets, free prose bodies, extension fields — is what forces the blob carrier and the HTML-comment machinery to exist at all.
Goal: design ONE canonical entry format whose READABLE form is directly representable in a tracker — tracker-AGNOSTIC (general use: GH Issues, GitLab, Jira-class, others via the BD-060 TrackerProvider abstraction), GENERAL (not GH-specific), and self-sufficient: no base64/gz64 blobs, no HTML comments, no hidden carriers needed for lossless representation. Then RE-AUTHOR ALL BD entries to comply, preserving each entry's content and intent (form changes, meaning does not — per the user's standing rewrite constraint).
Scope: the canonical format specification (fixed field set, status vocabulary, body shape, provider-safe constraints sized against the external-rules censuses) covering ALL entry types needed to represent phase-parts — not just backlog BD entries, but phases, parts, and tasks (the BD-185 phase-part structure must round-trip through this format, which is why BD-185 blocks this entry); the full re-author of every entry in `/backlog/` (and the project-side entry templates to the same standard); a permanent validator check enforcing the spec so drift cannot recur; the simplified tracker mapping the format enables (readable form == tracker form).
  **Structured `Blockers:` + tree-level Blockers-cycle validator (US-3, re-anchored 2026-06-13).** The canonical format makes `Blockers:` a machine-parseable STRUCTURED field (not free prose). The tree-level Blockers-cycle validate-pack check SHIPS WITH this format validator (it is re-anchored here from "the first Track-2 execution batch" because the cycle check is not cleanly implementable until Blockers is structured — MEASURED: a regex-edge cycle detector finds 17 false-positive cycles on the current free-prose tree, and an allowlist admitting them would also admit real future cycles, defeating the guard; EE-11). Once Blockers is a structured field the cycle check is exact. The original BD-094↔BD-095 data defect is verified fixed (EE-11).
Out of scope: any tracker migration execution (BD-204/BD-207 resumption — this BD only unblocks them); the v11.0 tracker-artifact cleanup (BD-214 does that now, in the existing format).
Acceptance criteria: a one-page normative format spec approved by the user; 100% of entries conform (validator-enforced, grep-zero on non-conforming patterns); every rewritten entry preserves content + intent; the format demonstrably round-trips through at least the GH provider with NO blob/comment carrier; the validator check is permanent CI.
References: BD-185 (the flat-file phase-part structure this format must round-trip — blocks this entry); BD-204 + BD-207 (the deferred tracker work this unblocks); BD-214 (the v11.0 cleanup that precedes it); BD-060 (TrackerProvider abstraction); BD-203 (per-entry flat-file standard); the BD-204 GH-rules census + tracker-landscape census (provider-constraint inputs).
