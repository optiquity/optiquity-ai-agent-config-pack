**BD-237 — Graphify graph-freshness mechanism is broken in production: redesign the auto-refresh + add verification checks (BD-225 shipped an un-verified, hand-installed, fragile hook that never ran)**
Type: fix/feat — STRUCTURAL pack-ops tooling. Redesign the Graphify graph-update mechanism so it refreshes reliably AND is verified to actually work, replacing the BD-225 hand-installed-hook approach. Full pipeline (architect → planner → coder; optional docs-researcher to verify graphify's real capabilities).
Status: Open
Target: v11.0 — URGENT. Graph is PACK-OPS-only (not shipped to clients), but a broken shipped mechanism with a three-failure defect; the user halted all other v11.0 work to fix it now (2026-06-19: "everything immediately stops until this is solved").
Blockers: none. RUNS NEXT — before resuming BD-206 (user 2026-06-19). Reconciles with the BD-226 worktree path-injection contract (Resolved) and is related to but distinct from BD-234 (graph cost/cadence assessment — that is a burn-in ASSESSMENT; this is the urgent mechanism FIX).
Provenance: discovered 2026-06-19 — Pack Chat checked whether the graph was updating per commit/push and found it FROZEN since the initial build (2026-06-18 22:56). NO post-commit hook is installed (the shared common `.git/hooks` dir does not even exist); `git push` never triggered any refresh; every 2026-06-19 commit (the BD-226 cluster, BD-236, BD-235) is newer than the graph. THREE FAILURES (user): (1) implemented wrong — the mechanism never ran in production; (2) the BD-225 reviewer did not catch it; (3) no check verified it worked, so it rotted silently.
Root cause (measured 2026-06-19, HEAD `fd22afb`):
  - **Fragile, un-verified mechanism (BD-225).** `pack-ops/OPTIONAL-FEATURES.md` §"How to keep it fresh" (L444-448) shipped the maintenance mechanism as a MANUAL, per-clone, HAND-INSTALLED `.git/hooks/post-commit` recipe — verbatim: *"hand-installed at `.git/hooks/post-commit` … It is NOT a committed file … so each clone installs it."* No auto-install, no verification. It was never installed here → graph frozen at its single initial build.
  - **Worst-of-the-menu choice.** BD-225 implemented a **post-commit, doc-gated SEMANTIC** hook (can auto-trigger the subscription semantic `extract`, `--backend claude-cli`) placed in un-versioned `.git/hooks`, rather than the safer shareable option the source guide offered (see source-guide note).
  - **Worktree reality unreconciled.** This repo runs as linked git worktrees; hooks live in the shared common `.git/hooks` dir (absent here); the hook's `$(git rev-parse --show-toplevel)/graphify-out/graph.json` resolution is the exact problem BD-226 fixed for spawned AGENTS — but the HOOK recipe (BD-225, predates BD-226) was never reconciled.
  - **No production-verification.** `scripts/validate-pack.py` carries ONLY Check 63 (`graphify-out/` never TRACKED). There is NO freshness check, NO hook-installed check, NO staleness gate. `graphify check-update` (the documented "cron-safe net") is wired into nothing that runs.
  - **Source-guide contribution (partial — answers "QuickStart error vs here-fault"):** the source QuickStart (`dshanenyc-mac-setup/docs/graphify/REPO-QUICKSTART.md` §"Keeping the graph fresh") actually offered SAFER options BD-225 did NOT adopt — Option B: a free **code-only `pre-commit`** hook (zero-token, never the subscription semantic pass), shareable via a tracked `.githooks/` + `git config core.hooksPath`. It ALSO over-promised Option C, `graphify hook install` ("graphify ships its own git hooks"), which **DOES NOT EXIST in graphify 0.8.39** (verified against `graphify --help`: there is no `hook` subcommand). NET: a small accuracy error in the source guide (a non-existent command) PLUS the larger fault — a fragile mechanism + zero verification — was implemented HERE in BD-225, which also failed to adopt the guide's safer shareable option.
Scope (redesign — the architect weighs options, reaches its own recommendation):
  - **Reliable auto-refresh that does not depend on a human hand-copying an un-versioned hook.** Candidate mechanisms (non-exhaustive, architect-evaluated with pros/cons): a tracked `.githooks/` + `core.hooksPath` hook running the free code-only `update`; wiring the refresh into `pack-startup` and/or Pack-Chat's own commit flow; graphify's built-in hook installer IF it actually exists (VERIFY — do not assume; the QuickStart already over-promised it). Reconciled with the worktree/common-hooks reality + the BD-226 path-injection contract.
  - **A production-verification check (the systemic remedy for failures 2 + 3).** A `validate-pack` check and/or `pack-startup` check that detects a stale or never-refreshed graph (and/or a missing/inert refresh mechanism) and FAILS LOUD, so silent rot cannot recur. Freshness criterion designed measure-then-bound (e.g. graph newer than HEAD's touched indexable files, or `check-update` clean, cheap O(1) per `ci-check-runtime-compounding`).
  - **Correct trigger.** NOTE: there is no standard client-side "post-push" git hook; the architect chooses the correct trigger (post-commit / pre-commit / pre-push / a workflow wrapper) to satisfy the intent — the graph refreshes as part of the normal git workflow AND a check proves the refresh ran.
  - **Cost discipline.** Keep the semantic pass (subscription via `--backend claude-cli` — NEVER an API key) a DELIBERATE main-session/orchestrator action; only the free, zero-token code-only `update` is safe to automate unattended — unless the architect justifies otherwise.
  - **Verify graphify's ACTUAL capabilities** (hook installer? `check-update` semantics? `extract`/`update` behavior?) against the installed 0.8.39 — flag-don't-guess (`verify-availability-not-just-existence`); a narrow docs-researcher pass if internal verification is insufficient.
  - **Doc correction:** correct the source/SETUP docs' inaccurate `graphify hook install` claim (or confirm the real availability) so the runbook matches reality.
Pipeline: (optional `pack-docs-researcher` to verify graphify hook/check-update/extract capabilities against 0.8.39) → `pack-architect` (refresh-mechanism options + the verification-check design, reconciled with worktree + BD-226) → user decision → `pack-planner` → `pack-coder`, under the bounded review/fix cycle.
Acceptance criteria: the graph refreshes automatically + reliably WITHOUT depending on an un-versioned hand-installed hook; a production-verification check (CI and/or `pack-startup`) FAILS LOUD on a stale/un-refreshed graph or an inert mechanism; the design is reconciled with the worktree/common-hooks reality + the BD-226 path-injection contract; the mechanism is verified against graphify's ACTUAL installed capabilities (not assumed); the inaccurate `graphify hook install` runbook claim is corrected or its real availability confirmed; `validate-pack` green; PACK-OPS-only (the graph does not ship to clients — no client-install/boundary regression).
