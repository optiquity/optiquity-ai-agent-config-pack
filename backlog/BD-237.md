Root cause (measured 2026-06-19, HEAD `fd22afb`):
  - **Fragile, un-verified mechanism (BD-225).** `pack-ops/OPTIONAL-FEATURES.md` §"How to keep it fresh" (L444-448) shipped the maintenance mechanism as a MANUAL, per-clone, HAND-INSTALLED `.git/hooks/post-commit` recipe — verbatim: *"hand-installed at `.git/hooks/post-commit` … It is NOT a committed file … so each clone installs it."* No auto-install, no verification. It was never installed here → graph frozen at its single initial build.
  - **Two real mechanisms, neither set up.** graphify 0.8.39 ships a built-in `graphify hook install` (code-only `post-commit`+`post-checkout`, worktree-aware) for the CODE layer — `graphify hook status` here reports BOTH `not installed`. The SEMANTIC layer needs a separate deliberate refresh (the hand-written `post-commit` running `graphify extract . --backend claude-cli`, or a main-session pass) — never set up either. BD-225 documented the hand-written semantic recipe but installed NOTHING and added no verification.
  - **Worktree reality unreconciled.** This repo runs as linked git worktrees; hooks live in the shared common `.git/hooks` dir (absent here); the hook's `$(git rev-parse --show-toplevel)/graphify-out/graph.json` resolution is the exact problem BD-226 fixed for spawned AGENTS — but the HOOK recipe (BD-225, predates BD-226) was never reconciled.
  - **No production-verification — and the obvious primitives are the WRONG ones.** `scripts/validate-pack.py` carries ONLY Check 63 (`graphify-out/` never TRACKED) — NO freshness check, NO hook-installed check, NO staleness gate. And `graphify check-update` always exits 0 while the `needs_update` flag tracks only pending NON-code changes (cleared on every code rebuild) — neither detects "graph behind HEAD." The VERIFIED-reliable signal is `graph.json`'s `built_at_commit` SHA vs `git rev-parse HEAD` (graphify ships no command for this comparison — a check must implement it); `graphify hook status` is a real scriptable installed-check for the code hooks.
  - **Origin — corrected 2026-06-19 (via `pack-docs-researcher` + direct CLI verification): the fault is HERE, not in the source guides.** The source QuickStart (`dshanenyc-mac-setup/docs/graphify/REPO-QUICKSTART.md` §"Keeping the graph fresh") is ACCURATE: it correctly describes `graphify hook install` as code-only and correctly states the SEMANTIC refresh needs a SEPARATE hand-written hook. `graphify hook install`/`uninstall`/`status` DO exist in 0.8.39 (`graphify --help` L92-94; `graphify hook status` runs and reports both code hooks "not installed"). An earlier Pack-Chat analysis wrongly claimed the command did not exist and that the guide over-promised it — both FALSE (caused by a truncated `--help` read). The real fault: BD-225 installed NEITHER the built-in code hooks (`graphify hook install`) NOR any semantic refresh, and added no verification; the BD-225 review did not catch it.
Scope (redesign — the architect weighs options, reaches its own recommendation):
  - **Reliable auto-refresh that does not depend on a human hand-copying an un-versioned hook.** Candidate mechanisms (non-exhaustive, architect-evaluated with pros/cons): a tracked `.githooks/` + `core.hooksPath` hook running the free code-only `update`; wiring the refresh into `pack-startup` and/or Pack-Chat's own commit flow; graphify's built-in `graphify hook install` (CONFIRMED in 0.8.39 — code-only `post-commit`+`post-checkout`, worktree-aware) for the CODE layer + a deliberate subscription mechanism for the SEMANTIC layer. Reconciled with the worktree/common-hooks reality + the BD-226 path-injection contract.
  - **A production-verification check (the systemic remedy for failures 2 + 3).** A `validate-pack` check and/or `pack-startup` check that detects a stale or never-refreshed graph (and/or a missing/inert refresh mechanism) and FAILS LOUD, so silent rot cannot recur. Freshness criterion = `graph.json` `built_at_commit` vs `git rev-parse HEAD` (VERIFIED reliable; NOT `check-update`/`needs_update`, which answer the wrong question), cheap O(1) per `ci-check-runtime-compounding`; plus `graphify hook status` for the code-hook-installed check.
  - **Correct trigger.** NOTE: there is no standard client-side "post-push" git hook; the architect chooses the correct trigger (post-commit / pre-commit / pre-push / a workflow wrapper) to satisfy the intent — the graph refreshes as part of the normal git workflow AND a check proves the refresh ran.
  - **Cost discipline.** Keep the semantic pass (subscription via `--backend claude-cli` — NEVER an API key) a DELIBERATE main-session/orchestrator action; only the free, zero-token code-only `update` is safe to automate unattended — unless the architect justifies otherwise.
  - **graphify capabilities — VERIFIED (done 2026-06-19).** The `pack-docs-researcher` pass is captured in `/tmp/pack-handoff-bd237-research/CAPABILITY-REPORT-BD-237.md` (preserve into `maintenance-docs/v11-implementation/` with the BD-237 work): `hook install` exists (code-only, worktree-aware); `update` is code-only/builds-if-missing; `extract` cache is content-keyed/incremental; `--backend claude-cli` = subscription/no-key; `check-update`/`needs_update` are NOT "graph behind HEAD" signals; `watch` is a foreground daemon. The architect designs on these verified facts (`verify-availability-not-just-existence` satisfied).
  - **Doc accuracy (verified — no correction needed).** The source/SETUP guides AND `pack-ops/OPTIONAL-FEATURES.md` §5.1/§5.2 are ACCURATE about `graphify hook install` (exists, code-only) and the separate semantic hook. (graphify's OWN `merge-driver --help` string "set up via hook install" is misleading upstream, but that is not a pack doc.) The architect re-confirms `OPTIONAL-FEATURES.md` still matches the redesigned mechanism after the fix lands.
