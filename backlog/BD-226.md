Description:

  **STATE IT GENERALLY (orchestrator + its agents), then re-apply to each surface.** The user's explicit instruction: generalize the rules, then apply them to the project's workflows for project use — do NOT write a pack-only rule.

  **SCOPE — WHERE, not HOW (user 2026-06-17).** This BD does NOT change the existing workflow: the agent roles, the bounded review/fix cycle, the spawn/triage/commit-approval gates, and the commit discipline all stay EXACTLY as they already are. It ONLY changes WHERE the work happens (which tree each agent runs in) plus the patch-handoff that FOLLOWS from keeping work in the worktree until review-clean. Every rule below is a placement/handoff overlay on the UNCHANGED workflow — read it that way; it should make this BD EASIER (relocate the process, do NOT redesign it). The only exception is a point of TRULY UNRESOLVABLE ambiguity, which the orchestrator surfaces to the human rather than deciding (per rule 9's general principle).
  **THE GENERALIZED MODEL (the rules, as refined with the user 2026-06-17):**
    1. **Default by agent class.** **Read-WRITE agents** (coders, fix-coders — anything that writes/mutates) run in an **isolated worktree**. The **FIRST coder of a commit establishes (creates) a fresh isolated worktree**; **every subsequent read-write agent in that same commit's cycle — fix-coders included — REUSES that same worktree. NEVER create a new worktree for a fix-coder.** **Read-ONLY agents** (reviewers, architects, planners, auditors, docs-researchers) run **in whatever tree their target work lives in**: the **main/canonical tree when that work is on HEAD/committed**, the **isolated worktree when the work is still uncommitted there**. (Read-only is NOT "always in-place" — it goes to where the work is.) **When a live worktree with uncommitted work is in play and the agent is NOT the standard cycle's own reviewer/fix-coder, the orchestrator does NOT self-judge the target's span — it ASKS the human (see rule 9).**
    2. **The governing bias.** NEVER apply, patch, or commit known-buggy or not-yet-reviewed work to the canonical tree (the pack repo's main checkout, or the client project's tree).
    3. **Per-commit worktree + in-worktree review/fix cycle.** Each new commit's first coder gets a fresh isolated worktree (rule 1). The **ENTIRE review/fix cycle for that commit runs inside that one worktree** — the read-only reviewer(s) and the fix-coder(s) all operate there. Nothing reaches the canonical tree mid-cycle.
    4. **Patch only after review-clean.** Read-write agents do **NOT** emit a patch up front (the work may be wrong). The patch is produced **only after a read-only reviewer (or other RO agent) confirms the work CLEAN**, by **SendMessage-ing the most-recent read-write agent** in that cycle to produce it. The orchestrator then applies that reviewed-clean patch to the canonical tree and commits (with the human's approval). → the canonical tree only ever receives reviewed-clean work, at commit time.
    5. **Bounded cycle (unchanged).** ≤2 review/fix pairs + 1 final review per commit; architect escalation if still dirty after the final pass. Only WHERE the cycle runs changed (the commit's worktree), not the cycle limits.
    6. **Agent spawning.** Each spawn is a fresh, clean-context agent UNLESS SendMessage is used (the deliberate exception that re-engages an existing agent — e.g., the post-review-clean patch step in rule 4).
    7. **Worktree lifecycle.** Fresh worktree per commit's first coder; **after a commit lands, explicitly REMOVE every orphaned worktree from that commit's cycle** — *after* the commit (safe by then), **not** right-after-use (it may be needed again mid-cycle), and **never** by relying on auto-removal.
    8. **Mechanics.** Isolated worktrees ALWAYS base at local HEAD (`worktree.baseRef:"head"`). An agent operating in a pre-existing worktree (the reviewer/fix-coder in the first coder's worktree) `cd`s into it and VERIFIES pwd/HEAD at runtime, operating only there. Agents NEVER commit/stage/apply — only the orchestrator applies the final clean patch and commits, with human approval.
    9. **Live-worktree gate — ASK, don't self-judge (refined live with the user 2026-06-17; corrects a mid-BD-221 placement error).** The only thing the orchestrator can evaluate with CERTAINTY is the detectable fact that an isolated worktree with uncommitted work exists (`git worktree list` + `git -C <wt> status`). It CANNOT reliably self-judge whether a given agent's *target* reaches into that uncommitted state — so it MUST NOT decide placement by that judgment. (a) **Standard cycle** — a commit's own reviewer/fix-coder is RULE-FIXED to the commit's worktree (rule 3): no judgment, no ask. (b) **Any OTHER agent** (an architect, a fix for a surfaced cross-cutting issue, a new task) spawned WHILE a live worktree with uncommitted work exists: the orchestrator ASKS the human BOTH — (i) PLACEMENT (which tree the agent runs in) and (ii) DISPOSITION (reuse vs abandon that worktree); it NEVER self-decides either. Reuse and abandon are both legitimate per-case (the work may be salvageable, or it may have to be discarded for a fresh worktree) — the human decides. (c) **Mixed-target:** when an agent's target genuinely spans committed + uncommitted state, the commit's worktree is the SUPERSET and the correct home — but the orchestrator does NOT assume it can detect that span; it asks. **General principle:** when uncertain that a rule's CRITERIA are guaranteed-evaluable, convert the rule to an ASK rather than applying it autonomously.
    10. **Parallelization + dependency map (architect/planner deliverable — its OWN section; added 2026-06-18, user direction).** For any multi-commit effort, the architect and planner MUST identify which commits/tasks can run in PARALLEL (independent; safely isolatable in concurrent worktrees) versus which carry DEPENDENCIES (on other commits, shared files/contracts, ordering, or any external factor) and must run serially. This analysis lives in its OWN dedicated section of the design/plan — NEVER woven inline into the other parts — so it stays tightly coupled to (and references) those parts WITHOUT guiding or biasing their design/planning. Per commit/task the map names its dependencies (or "none") and the safe parallel-wave group it belongs to; the orchestrator consumes the map to schedule parallel worktree waves vs serial commits (rule 1).
