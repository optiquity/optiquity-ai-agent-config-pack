**BD-282 — Migrator pause is mislabeled "migration failed": the framework exit-trap alarms on a deliberate customization pause — reword to "paused — requires attention" and present clear reconciliation options + exact commands**
Type: bug/UX — migrator framework pause-message accuracy (launch-relevant migration UX; NOT a data-safety defect — the pause + resume behavior is correct).
Status: Resolved
Target: v11.0 (surfaced during the BD-205 W3 real-content migration re-run, 2026-08-11; launch-relevant client-facing UX). Lands in v11.0 per no-deferral unless the user explicitly defers.
Blockers: None.
Unblocks: a client who hits the (correct) customization pause during a v10→v11 migration sees calm, actionable guidance — not a false "migration failed".
File/Symbol: `scripts/lib/migrator-core.sh` (~L209 — the generic exit/trap handler that emits `warn "migration failed (exit $rc); partial report rendered …"` on the pause exit); `scripts/lib/migrate-v10-to-v11/apply.sh` (the pause path ~L221-266 that already emits the good "PAUSED — customization-detected-needs-reconciliation" block + per-sidecar options (a)/(b) + the `--resume` command); `scripts/lib/customization-report.sh` (the report's "Files needing manual reconciliation" section) — architect confirms the exact surface set; the migration tests that assert the pause messaging.
Description:
  **Problem (observed, BD-205 W3 re-run, 2026-08-11):** on a real client v10 tree with customizations, `--apply` correctly detected 5 customizations and PAUSED for reconciliation (exit 0, safe, resumable). But immediately after the (good, detailed) "PAUSED" block, the framework printed:
  `warning: migration failed (exit 0); partial report rendered to …/report.md`
  The migration did NOT fail — it paused deliberately (exit 0) and completed cleanly on `--resume`. "migration failed" is alarming and misleading; a real client could reasonably think the migration broke and abort or panic.
  **Root cause:** `scripts/lib/migrator-core.sh` (~L209) — the generic framework exit/trap handler treats the pause's non-completion exit as a FAILURE and prints "migration failed (exit $rc)". It does not distinguish a deliberate, resumable customization pause from a genuine error. The v10→v11 apply path (`apply.sh`) already prints a correct, detailed PAUSED block just above it, so the framework line contradicts the adapter's own (accurate) message.
  **Goal (user spec, 2026-08-11):** the pause is presented as a calm, attention-requiring checkpoint, not a failure — e.g. **"Migration paused — requires attention"** — and it enumerates the RECONCILIATION OPTIONS the user can take (accept the pack's version / keep your customization / merge by hand / any other supported path — labeled with each option's consequence) with **specific, copy-paste-ready commands** for each, plus the exact `--resume` command to continue.
  **Design questions (architect decides; do not pre-pick):**
   (1) How should the framework DISTINGUISH a deliberate pause from a real failure — a pause sentinel (e.g. `sentinels/stage-S3.paused`), a dedicated exit code, or an adapter-set flag — so `migrator-core.sh` reworders only the pause case and still reports genuine failures loudly?
   (2) Where does the pause-vs-failure awareness live — the generic framework (`migrator-core.sh`), the adapter (`apply.sh`), or a shared helper — given the framework is migrator-agnostic and must not hard-code v10→v11 specifics?
   (3) What are the OFFERED options and their exact commands — including whether to add a convenience one-shot for "apply the recommended resolution" (e.g. accept-pack-for-all or mark-all-resolved) versus only documenting the existing per-sidecar (a)/(b) paths; "recommended" must be defined honestly (a customization conflict has no universally-correct auto-resolution, so any convenience command must state what it discards/keeps).
   (4) Consolidate vs layer: the adapter's existing PAUSED block is already good — decide whether the fix is (i) suppress/replace only the misleading framework line, (ii) enrich the adapter block with the copy-paste commands, or (iii) both, avoiding a duplicated/again-contradictory message.
  **Not a data-safety defect:** the pause/detect/resume behavior is correct and proven (BD-205 W3). This is purely the exit-message UX.
  **Provenance:** surfaced by the BD-205 W3 real-content migration re-run (2026-08-11), user-flagged; pre-existing framework behavior; launch-relevant (first-run client migration UX at v11.0 launch).
Acceptance criteria: a deliberate customization pause NEVER prints "migration failed"; it presents a calm "paused — requires attention" framing with the reconciliation options + exact copy-paste commands + the `--resume` command; a GENUINE migration failure still reports loudly as a failure (the reword must not swallow real errors); no duplicated/contradictory pause vs failure messaging; the `--apply`/`--resume` control flow + exit codes are unchanged (or changed only as the design requires, with tests updated); the migration test suite asserts the new pause messaging (and that a real failure still reads as failed); `validate-pack` green; the full migration + tracker-migrate battery (both jobs + `PACK_VALIDATE_DEEP=1`) passes.
References: BD-205 (W3 testbed re-run that surfaced this); BD-281 (sibling migrator dry-run UX fix — adjacent files `migrator-manifest.sh`/`migrator-stages.sh`; coordinate the migrator-lib blast-radius); BD-119 (`maintenance-docs/v11-implementation/ARCHITECTURE-BD-119.md`, migrator framework contract — `migrator-core.sh` is the framework core).
Resolved: 2026-08-11 — fixed via the full LARGE pipeline (architect → adversarial architect [found 2 real MUSTs] → reconciliation architect → user design gate → coder → review, all resolved CLEAN). Added a generic framework primitive `migrator_pause` (sets `_MIGRATOR_PAUSED`, exits 0) that the v10→v11 adapter calls instead of a bare `exit 0`; `scripts/lib/migrator-core.sh`'s exit-trap now branches on the flag — a deliberate customization pause renders a "PAUSED for customization reconciliation" report title + a calm `note:` stderr pointer (no "migration failed"), while a genuine failure keeps the byte-unchanged "migration failed (exit N)" wording. `apply.sh`'s pause block reworded to "Migration paused — requires attention" with three consequence-labeled options (accept-pack `rm` / keep-yours `mv` / merge-by-hand `touch .resolved`) + per-sidecar copy-paste commands + an honest accept-pack-for-all one-liner + the `--resume` command; `customization-report.sh` intro enriched abstractly + conditionally. Genuine-failure preservation is STRUCTURAL (the PAUSED branch fires only on `_MIGRATOR_PAUSED==1`, set only on the deliberate pause path) and proven by a bite-verified test — a real post-dispatch/pre-report `exit 42` still reads "migration failed (exit 42)" (the adversarial pass corrected the original test, which had targeted a gate failure that never routes through the trap). `migrator_pause` inventoried in Check 26 + `test-migrator-core.sh` + `ARCHITECTURE-BD-119.md` (lock-step per enumerate-encoding-surfaces). Full migration + tracker battery (1090/0) + `validate-pack` (both jobs + `PACK_VALIDATE_DEEP=1`) green; apply/resume control-flow + exit codes byte-unchanged. 7 files (C1–C7).
