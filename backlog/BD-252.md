**BD-252 — Pack-side resumable session-state mechanism (repo-committed, CLI-agnostic, current-snapshot-only, /pack-startup-wired, CI-enforced)**
Type: feat — STRUCTURAL (new convention + new mechanism + new CI check(s) + /pack-startup integration + cross-CLI). Surfaced 2026-06-28 from the pack-operations status/notes resilience gap (Pack Chat's live orchestration state lived only in volatile chat context + a CLI-memory note + a gitignored per-clone spawn-registry); user-directed open.
Status: Resolved
Target: v11.0 (default per no-deferral-without-user-direction; NOT strictly launch-blocking — pack-dev-process resilience, not a client-shipped feature; sequenced AFTER BD-234 in the v11.0 launch queue, user-confirmed)
Blockers: none hard. Coordinate with BD-232 (memory-cache reorg) on the CLI-memory boundary; BD-252 designs the resumable-snapshot pattern that BD-253 (project-side sibling) then adapts.
Unblocks: a Pack Chat session that is fully transferable + restartable — survives /pack-startup, machine transfer, and CLI transfer (Claude ↔ Codex ↔ Antigravity) — with nothing necessary-to-resume lost.
Problem: Pack Chat's LIVE orchestration state (which agents/work are in flight, what is queued and in what order, whether the current phase is parallelizable, the in-flight decisions needed to resume mid-BD) currently lives in the volatile session chat context + a CLI-memory CARRY-OVER note + a gitignored per-clone spawn-registry. None of that transfers: a /clear, a context compaction, a move to another machine, or a switch to another CLI loses the live state. CLI memory is per-machine/per-CLI → not transferable. So a session interrupted mid-BD cannot be reliably resumed elsewhere.
Requirements (FIRM):
  - **Repo-committed** state artifact (a doc or other repo file) — the repo is the memory, so the state travels with the repo.
  - **CLI-agnostic / trinity-agnostic** — identical mechanism + format across Claude Code, Codex, and Antigravity; no CLI-specific feature.
  - **CLI memory FORBIDDEN for state** on every CLI platform (Claude `~/.claude` memory, Codex/Antigravity equivalents). State must not depend on anything that does not travel with the repo.
  - **Transferable + restartable** — survives /pack-startup (which READS the snapshot and SETS the resume state), a machine transfer, and a CLI transfer (any of Claude/Codex/Antigravity → any other), with the entirety of what is necessary to resume preserved.
  - **Pause/resume model** — on save, all spawned agents + work are PAUSED; the snapshot may sit mid-one-or-more-BDs. Resume = RE-SPAWN the in-flight work from the snapshot; the last commit is the durable boundary (uncommitted in-flight agent edits are re-done, not preserved).
  - **Parallelization mode is part of state** — the snapshot captures whether the current work is parallelizable or serial, plus the queue order; a session may transition parallelizable ↔ serial and the snapshot must reflect the current mode.
  - **Current-snapshot-ONLY, never history** — the state is always the current snapshot of what is happening + what is queued + in what order. It is NEVER a historical record. History is preserved by OTHER mechanisms (BD/changelog entries, commits, handoff/maintenance docs), completely ISOLATED from this one.
  - **Consistency / no-stale enforcement** — wired into pack operations so Pack Chat updates the state on every state change; nothing may go stale. CHECKS (CI / validate-pack) ENFORCE this — the architect designs the enforceable checks (candidates: structural validity of the snapshot, freshness vs HEAD, and a no-history guard so the snapshot cannot accrete a historical record).
  - **/pack-startup integration** — /pack-startup reads + reports + primes the resume from the snapshot.
Architect-to-decide (design charges — do NOT pre-decide):
  - **State boundary (Q2):** the exact set of what must be persisted to resume vs what can be lost / easily recreated. Driving principle: anything NEEDED to resume must be in the repo-snapshot; the expectation is CLI memories are either unneeded or trivially recreatable. The architect determines the precise boundary.
  - **Spawn-registry fate (Q4):** investigate `graphify-out/.pack-spawn-registry.jsonl` — WHAT it saves, WHY it is untracked, and which parts are HISTORY (record-only) vs RESTORE-state. Then recommend: if the registry and this snapshot are two parts of the SAME thing → ONE mechanism (supersede/retire the registry); if ENTIRELY SEPARATE things → TWO mechanisms. Governing rule: history is NEVER persisted by the state mechanism; if history must persist it uses a SEPARATE, isolated mechanism; only restore-state lives in the snapshot.

  **Out of scope:** the project-side PM-Chat session-state (BD-253); history persistence (the existing BD/changelog/commit/handoff mechanisms — kept isolated); the broader CLI-memory cache reorg (BD-232) beyond the state boundary this BD draws.
