## §1 Root cause (grounded)

**RC-1 — platform guard, path-prefix-scoped, non-disableable.** Claude Code's worktree-isolation guard blocks, pre-execution, EVERY git invocation from a worktree-isolated agent whose cwd or redirect resolves to the main checkout — read-only verbs included (EEB-2) — and the protected target is the main checkout's PATH PREFIX, which includes every linked worktree at the standard `<main>/.claude/worktrees/` location (EEB-3). The enforcement is documented, hardened in v2.1.203/v2.1.210, and cannot be turned off (EEB-6). Non-git access (Read tool, plain `cd`) crosses trees freely (EEB-2). The guard's command-shape matcher additionally false-positives on git-free `GIT_DIR=`-shaped text (EEB-21) — a measured bound the workspace practice note and the W0 gate both address.

**RC-2 — the `full` contract instructs exactly the blocked operation.** Every mode-contract surface states "spawn into an isolated worktree, then `cd` to the target tree" with no post-`cd` constraint (census claim A; EEB-8). When the target is the main checkout, the instructed `cd … && git …` is the guard's textbook deny case (probe 1 reproduced it 11/11). Additionally, `cd` does not persist between subagent Bash calls (census §4.1), so the contract's single-`cd` framing was never mechanically accurate.

**RC-3 — the cycle-reuse contract is broken by the same finding, in BOTH modes.** The fix-coder contract ("REUSES the first coder's worktree — the fix-coder `cd`s in + verifies pwd/HEAD", P3:311–314; pack-coder def :42–44; pack OPTIONAL-FEATURES :117–140; client PM-CHAT :516–519, coder.md :58–63; the full carrier universe in EEB-10) sends an ISOLATED RW agent into an in-prefix sibling worktree: its `git rev-parse`/`git status` verify step is measured-blocked (EEB-3), and its Edit/Write there is the guard's documented file-edit target class. This breaks under the DEFAULT mode too (RW agents isolate in both modes), so BD-290 is a subsystem repair, not a `full`-mode patch. Under `full` the same U2 finding also cuts off the rule-8 reviewer-of-uncommitted-work (an isolated RO agent cannot git a commit worktree under the prefix) — including the client-shipped reviewer prompt template that instructs exactly that step (EEB-20-b).

**RC-4 — why `full` must work (the forcing function).** Under the default mode, non-isolated RO teammate spawns ride the mailbox channel: completion notifications are lost and platform bug #73647 (verified open, census §4.6) prepends boilerplate to every delivery. Measured on 2.1.245: the isolation parameter selects the clean async completion channel (EEB-7). `full` is the durable channel-hygiene lever — but only if its git story is platform-legal.

**Non-causes (verified):** the pack's PreToolUse hooks (no denial names any repo hook — probe 1 §4; the hooks enforce the spawn parameter only, EEB-15); the config-read idiom; graph-path injection (already worktree-aware).

## §3 The shared commit workspace — cycle flows + rule-8 resolution (mode-invariant)

**Problem.** Any multi-agent commit cycle needs one shared mutable tree: the first coder edits it, the reviewer verifies THE WIP STATE in it (including running the full CI battery — the `verify-full-ci-suite` rule binds coder AND reviewer), and the fix-coder continues in it. The platform's agent worktrees sit in-prefix, so from any ISOLATED agent they are git-unreachable (EEB-3) — which breaks the fix-coder in both modes and the reviewer under `full`.

**Design.** Per commit, the ORCHESTRATOR creates the workspace at an out-of-prefix path and injects its absolute path into every cycle spawn:

- Create: `git worktree add --detach <WS> HEAD` where `<WS>` = `${XDG_STATE_HOME:-$HOME/.local/state}/optiquity-pack-workspaces/<bd-or-batch>-<ts>/` (pack side; client analog under the client's persistent handoff root convention, mirror-but-customize). Detached-at-HEAD: no scratch branch to clean up; `git -C <WS> diff` is the patch source.
- Work: every cycle agent — first coder, reviewer(s), fix-coder(s) — targets `<WS>` by absolute path, fusing `cd <WS> && …` into each Bash call (cwd resets between calls; probes used exactly this form). RW edits use absolute `<WS>/…` paths.
- Spawn params unchanged: RW always `isolation:"worktree"`; RO per mode. The agent's own platform worktree becomes an untouched shell that the platform auto-removes ("removed automatically when the subagent finishes without changes", census §4.1) — the isolation param is retained for the guard-vs-main protection and the clean channel, not as the workspace.
- Verify (rule 8, executable again): `pwd`; `cd <WS> && git rev-parse HEAD` = injected SHA; `cd <WS> && git status` shows the expected WIP. All measured-legal forms (EEB-3 WT_OUT).
- Patch: unchanged rule-4 flow — after review-clean, re-engage the most-recent RW agent: `cd <WS> && git diff > <handoff>/changes.patch`; orchestrator `git apply --check` + `git apply` + commit (user approval). (The patch-emit compound is W0-gated below.)
- Teardown: orchestrator `git worktree remove <WS>` ONLY after the commit is confirmed landed — the EXISTING rule-7 semantics, now strictly required because the platform sweep never removes user-created worktrees (census §4.1 "It never removes worktrees you create").

**Why every step is legal.** Orchestrator `git worktree add/remove` runs in the unguarded main session. Agent git/cd against `<WS>`: measured allowed in the plain verb forms (EEB-3). Agent Write/Edit to `<WS>` paths: same out-of-prefix class as the measured handoff-dir report writes (EEB-5); the file-edit check's documented target is "a path in the main checkout". Test batteries run with `cd <WS> && …` — the command names an out-of-prefix cwd and no git redirect; git subprocesses inside a script are not tool-call text the guard inspects. Residual risk: the "command shape" matcher demonstrably false-positives on complex/env-var-shaped command lines (EEB-21) — mitigated by BOTH a documented practice note (keep workspace commands simple, one action per call) AND the W0 gate below, which measures the two correctness-bearing complex shapes before any coder wave.

**W0 gate (verify-availability — the complete unmeasured set, enumerated).** Four instances remain unmeasured, all gated here (EEB-5 proves only the plain-Write path class; EEB-3 proves only plain git verbs at the scratchpad path; EEB-21 documents the shape matcher's false positives): (i) isolated Edit/Write INTO a workspace worktree; (ii) a test-run with `cd <WS>` cwd; (iii) a realistic BATTERY shape; (iv) the PATCH-EMIT compound. W0 is a short orchestrator-run probe before any coder wave, with the scratch worktree created AT THE ACTUAL WORKSPACE ROOT (`${XDG_STATE_HOME:-$HOME/.local/state}/optiquity-pack-workspaces/w0-probe-<ts>/` — pinning the measured path class to the one the design ships): spawn one isolated probe agent to (a) Write a file there, (b) Edit it, (c) `cd <WS> && git status`, (d) `cd <WS> && python3 -c 'print(1)'`, (e) one realistic battery invocation — `cd <WS> && PACK_VALIDATE_DEEP=1 python3 scripts/validate-pack.py` (or one wired test script), (f) the patch-emit compound — `cd <WS> && git diff > <handoff>/w0-probe.patch`. All-pass ⇒ proceed; any fail ⇒ the fallback below (a fail on (e)/(f) alone may alternatively be absorbed by the practice-note decomposition — split the battery/patch call into simpler per-step forms — if a decomposed form passes in the same probe session).

**Fallback (only if W0 fails).** Prepared-worktree handshake: fix-coder/reviewer keep their own platform worktrees; the orchestrator transfers WIP by `git -C <WS_prev> diff > <handoff>/wip.patch` (orchestrator, read-only) and `git -C <wt_new> apply` (orchestrator — the sole patch-applier, per the existing principle) using a file-based handshake (agent writes its `pwd` to `<handoff>/worktree-path.txt`, poll-waits on `<handoff>/wip-ready.marker`). Fully specified so the planner can pivot without a new architect pass; NOT the primary because it adds a coordination protocol and still cannot give the reviewer a battery-runnable WIP tree without a second transfer.

**Rejected alternatives** (design-discipline-challenge, each with the disqualifying evidence):
1. *Injection-only for the reviewer* (probe 1's own recommendation, extended): orchestrator injects `git -C <wt1> diff` as a review artifact; reviewer Reads files. Rejected: the reviewer cannot RUN the CI battery against the WIP state (its own worktree lacks the WIP; the WIP tree is in-prefix) — a direct regression of `verify-full-ci-suite`. The injection mechanism itself is KEPT for non-cycle facts (S5).
2. *EnterWorktree*: documented as available from isolated subagents for `.claude/worktrees/` targets (census §4.1), which would re-pin the agent into the commit worktree. Rejected NOW: the tool is in NO pack/client agent's `tools:` line (measured: all defs carry `tools: Read, Grep, Glob, Bash, Write, Edit`), its post-enter guard semantics for subagents are unmeasured, and granting it widens every RO agent's capability surface. Recorded as a possible future simplification — a rejected alternative, not deferred work.
3. *Non-isolated exemptions under `full`* (reviewer/fix-coder spawn in-place): reintroduces the mailbox/boilerplate defect for the most frequent RO spawn class and, for RW, abandons the no-platform-safety-net protection. Rejected.
4. *Fresh-coder re-derivation* (fix-coder redoes work from reports): wasteful, error-prone for overlapping edits. Rejected.
5. *Agent-side `patch -p1` WIP reconstruction*: circumvents the `git apply` denial by tool substitution — permission-adjacent; rejected on rule-hygiene grounds.

**Containment analysis** (probe 2 anomaly 3, surfaced not tested). `<WS>` is outside the guard's protected prefix, so the platform does not mechanically stop a misbehaving agent's state-changing git there. Delta vs status quo: none material — an isolated agent can already run state-changing git in its OWN worktree (guard checks the TARGET TREE, not the verb), and under the default mode RO agents already run fully unguarded in the work's tree. The trust anchors remain what they are today: the `agents-never-commit` prose ban + rules-in-force blocks + the documented-optional `permissions.deny` recipe. The guard-vs-MAIN protection is retained for every isolated agent. This bound is documented as an honest-bounds caveat (§4 edit E-P4-d / E-C8-d).
