## §1 Executive summary

1. **Internal census.** The isolation-mode mechanism is encoded on **33 tracked surfaces** (17 pack-side operating/enforcement/test surfaces, 12 project-side client deliverables, 4 shared-token validator/manifest surfaces). The SSOT chain is: `pack-ops/OPERATING-MODES.md` (mode-family contract) → trinity `CLAUDE.md` §"Sub-agent behavior (Claude-only)" (spawn rule) → `pack-ops/PACK-CHAT.md` §"In-session sub-agent spawn + merge-back" (spawn preflight) → `scripts/hooks/modes-enforce.py` (mechanical backstop) → `.claude/skills/pack-isolation-mode/SKILL.md` ×3 CLI copies (selector) — mirrored project-side as `PM-OPERATING-MODES.md` / `PM-CHAT.md` / `pm-modes-enforce.py` / `pm-isolation-mode` SKILL.
2. **The `full`-mode contract is stated identically on every surface:** "All agents (read-only included) spawn into an isolated worktree, then `cd` to the target tree." No internal surface documents any constraint on what the isolated agent may do after the `cd`.
3. **Externally verified (official docs, retrieved 2026-08-25):** Claude Code **actively BLOCKS** commands from a worktree-isolated subagent whose working directory resolves to the main checkout, and **blocks git redirected into the main checkout** ("The redirect can come through `git -C`, `--git-dir`, a `GIT_DIR` or `GIT_WORK_TREE` variable, **or a `cd` into the main checkout before running git**"). This enforcement is documented as non-optional ("You can't turn this check off") and hardened in v2.1.203/v2.1.210. The internal `full`-mode contract ("spawn isolated, then `cd` to the target tree") and the documented platform enforcement are in direct tension **when the target tree is the main checkout** — reported here as a documented platform semantic, not a diagnosis.
4. **Channel semantics (externally verified):** a background subagent's results reach the parent "as a completion notification in a later turn" (sub-agents doc). BUT: with agent teams enabled, "a named subagent launches as a teammate," which "reports back through team messages rather than by returning a result" (agent-teams + tools-reference docs). **No official doc ties the result channel to the `isolation` parameter.** The docs key the channel on the named-teammate-vs-subagent launch path. The pack's belief that `full` isolation yields the async-task channel (BD-290 Unblocks line) has no documented basis found — marked as an unknown for the probe (§5-U3).
5. **Bug #73647 verified live:** anthropics/claude-code issue #73647 is OPEN (created 2026-07-03) — "Peer-message security boilerplate fires on idle_notification status pings"; the full injected-warning text is quoted in the issue and reproduced in §4.6.
6. **Hooks for subagents (externally verified):** settings-file hooks "also run inside subagents. When a subagent calls a tool, tool events such as `PreToolUse` and `PostToolUse` fire the same configured hooks as in the main conversation" — so the pack's PreToolUse[Agent] hook fires on the MAIN session's Agent call, and PreToolUse[Bash] hooks additionally fire on subagent Bash calls.
7. **Documentation gap found:** the official hooks reference documents Agent `tool_input` as `prompt` / `description` / `subagent_type` / `model` ONLY — the per-spawn `isolation` parameter the pack's hook keys on (`tool_input.get("isolation")`, modes-enforce.py:115) is NOT in the documented PreToolUse input table, though the parameter's existence is corroborated by issue #55708 and by the sub-agents doc's per-spawn framing. Whether the live PreToolUse payload actually carries `tool_input.isolation` is an explicit UNKNOWN (§5-U1) — the pack's hook unit tests use synthetic payloads and do not prove the live payload shape.

### §4.1 `isolation: worktree` — creation, base, cwd, lifecycle (DOCUMENTED)

Source: https://code.claude.com/docs/en/worktrees ("Run parallel sessions with worktrees") + https://code.claude.com/docs/en/sub-agents ("Write subagent files" / frontmatter table).

- Worktree location + branch: "the worktree is created under `.claude/worktrees/<name>/` at your repository root, on a new branch named `worktree-<name>`" (worktrees doc, §Start Claude in a worktree; subagent worktrees observed as `agent-XXXX` names per issue #55708's reproduction).
- Frontmatter field: "`isolation` … Set to `worktree` to run the subagent in a temporary git worktree, giving it an isolated copy of the repository **branched by default from your default branch rather than the parent session's `HEAD`**. The worktree is automatically cleaned up if the subagent makes no changes" (sub-agents doc, Supported frontmatter fields).
- Base ref: "Subagent worktrees use the same base branch as `--worktree`, so they branch from your repository's default branch unless `worktree.baseRef` is set to `"head"`." `baseRef` accepts `"fresh"` (default; branches from `origin/<default>`, kept current by a capped 5-second fetch when stale >24h, "falls back to your current local `HEAD`" if no remote/uncached) and `"head"`; "You can't set `worktree.baseRef` to a branch name." (worktrees doc, §Choose the base branch). This CONFIRMS P4:167-177/C8.
- cwd: "A subagent starts in the main conversation's current working directory. Within a subagent, `cd` commands don't persist between Bash or PowerShell tool calls and don't affect the main conversation's working directory." "A subagent with `isolation: worktree` runs its Bash and PowerShell commands inside its worktree." (sub-agents doc). **The internal contract's "`cd` to the target tree" therefore has no documented persistent-cd mechanism inside a subagent — each Bash call starts back in the pinned worktree cwd.**
- Lifecycle: "Each subagent gets a temporary worktree that Claude Code removes automatically when the subagent finishes without changes; a worktree with changes stays on disk until the periodic sweep … can remove it without losing work." "While an agent is running, Claude runs `git worktree lock` on its worktree." Sweep governed by `cleanupPeriodDays`; "It never removes worktrees you create with `--worktree`." (worktrees doc, §Isolate subagents with worktrees / §Clean up subagent and background-session worktrees). - `EnterWorktree` from an isolated subagent: "From within a worktree session, or from a subagent with a pinned working directory such as `isolation: worktree`, only the `path` form is available and the target must be under `.claude/worktrees/` of the session's repository" (tools-reference, EnterWorktree row).

### §4.2 What happens when an isolated agent targets a different checkout (DOCUMENTED — the load-bearing finding)

Source: https://code.claude.com/docs/en/worktrees §"How Claude Code enforces isolation" + https://code.claude.com/docs/en/sub-agents (same section, subagent-specific paragraphs).

Verbatim (worktrees doc): "While a session is isolated in a worktree, Claude Code blocks the tool calls the checks below define. … **The same enforcement covers every subagent Claude spawns from the isolated session.** … Claude Code applies four checks:
- **File edits**: Claude Code blocks an `Edit`, `Write`, or `NotebookEdit` that targets a path in the main checkout.
- **Command working directory**: Claude Code blocks a Bash, PowerShell, or Monitor command whose working directory resolves to the main checkout, **or whose working directory it can't verify stays outside it**.
- **Git redirects**: Claude Code blocks a Bash or Monitor command that redirects git into the main checkout. The redirect can come through `git -C`, `--git-dir`, a `GIT_DIR` or `GIT_WORK_TREE` variable, **or a `cd` into the main checkout before running git**.
- **Command shape**: Claude Code blocks a Bash or Monitor command it can't verify stays inside the worktree, even when the command runs no git at all. … **You can't turn this check off.**
The checks apply to the repository you launched Claude Code from. They also cover the main checkout a linked worktree is linked from. … Claude sees each refusal as a tool error that names the worktree and says how to proceed."

Verbatim (sub-agents doc): "A command whose working directory resolves to your main checkout instead … fails with an error. **Before v2.1.203, such a command could run in the main checkout.**" "This working-directory check covers the whole repository containing the directory you launched Claude Code from. … **Before v2.1.210, the check covered only the launch directory itself.**" "When the main conversation itself runs isolated in a worktree, Claude Code applies the same checks to the session and to every subagent it spawns, including subagents without `isolation: worktree`."

Factual consequence for claim A (stated without diagnosis): the internal `full`-mode contract instructs an isolated RO agent to `cd` to "the target tree"; when that target is the MAIN CHECKOUT, the documented enforcement **blocks every Bash command whose cwd resolves there and every git redirected there** — read-only git verbs included (the checks are not read/write-differentiated in the doc). Whether a `cd` to a DIFFERENT LIVE WORKTREE of the same repo (the rule-8 uncommitted-work case) is also blocked is not explicitly stated — the checks name "the main checkout" as the protected target — marked §5-U2 for the probe.

Historical corroboration: issue #55708 — "Agent tool's isolation: 'worktree' does not isolate git HEAD modifications — subagent's git checkout affects parent repo's branch" (created 2026-05-03, state closed, label `duplicate`) documents the pre-hardening era where a subagent's git could mutate the parent repo's HEAD; the v2.1.203/v2.1.210 "Before …" notes above are the documented hardening of exactly this surface. Retrieved 2026-08-25 via api.github.com/repos/anthropics/claude-code/issues/55708.
