## Findings

### Finding F1
- **Severity:** MUST
- **Location:** `cross-BD` — `scripts/lib/tracker-migrate-forward.sh:898, 924, 984` (step 7 + step 7b call sites) vs `scripts/lib/tracker-links.sh:182` (`tracker_links_create_blocked_by` orchestrator) and `scripts/lib/tracker-cycle-check.sh:163, 302` (cycle check + store-add).
- **Title:** Forward migration bypasses BD-108's link orchestrator → cycle store + sidecar `dependency_edges` not populated by initial migration
- **Description:** BD-108 ships `tracker_links_create_blocked_by` as the "single point of entry for creating cross-entity `blocks` / `blocked-by` edges across the V3.3 §5.1 entity graph" (per `tracker-links.sh:1-37`); the orchestrator runs cycle detection, calls `provider_link`, and persists the new edge to the cycle-graph store via `_tracker_cycle_check_store_add`. But the initial v11.0 forward migration's step 7 (`tracker-migrate-forward.sh:898, 924`) and step 7b (`tracker-migrate-forward.sh:984`) call `provider_link <src> <tgt> "blocked-by"` **directly**, completely bypassing `tracker_links_create_blocked_by`. Concrete consequences:
  - The cycle-graph store at `<repo>/.pack-tracker/links-graph.json` is NEVER created or populated by initial `pack tracker init` forward migration — only by subsequent `pack td promote --to=phase-N.M` calls (Path 2 via `tracker-promote.sh:837-922`). Cycle detection at link-create time therefore has zero baseline; cycles introduced by initial migration are invisible to the cycle check until at least one Path-2 promotion runs.
  - The sidecar's `phase_tasks[].dependency_edges` block (V3.3 §6.R; BD-106 emitter at `tracker-sidecar.sh:312`) is NEVER populated for v10-converted phase tasks — the forward migration walks the parser output but only emits `provider_link` calls, not sidecar block writes.
  - BD-108's IMPLEMENTATION-REPORT §10.4 acknowledges drift if a user manually edits the sidecar, but does NOT acknowledge that the forward migration itself is a primary source of drift on every fresh tracker enable.
- **Suggested fix:** Two options, both safe. (a) Re-route step 7's phase-N.M case (line 894-905) and step 7b's phase-task dep loop (line 966-989) through `tracker_links_create_blocked_by` instead of bare `provider_link`. The orchestrator handles cycle-check (which is a no-op on the empty initial store), persists the edge, and writes the sidecar (when the caller wires the sidecar-mutation callback per `tracker-links.sh:31-35`). This preserves the "single point of entry" architectural invariant. (b) Document the bypass explicitly in BD-108 §10.4 + add a "store rebuild from sidecar" verb to `pack tracker doctor` (BD-108 §10.4 already hints at this as a future BD). (a) is the architecturally consistent choice; (b) is a documentation-only mitigation. Recommend (a) as a follow-up BD; this batch ships with the gap as a known limitation if Pack Chat decides not to delay v11.0 ship.
- **Source:** ARCHITECTURE-V3.3-DELTA.md §5.5 (cycle detection runs at link-creation time) + §5.7 (forward step extension); BD-108 IMPLEMENTATION-REPORT §10.4 (cycle store / sidecar drift); `scripts/lib/tracker-links.sh:1-37` (single-point-of-entry contract).
- **Cross-cut?** **yes** — A per-BD reviewer for BD-108 would see only the `tracker-links.sh` file and the new step 7b in forward migrate, and would likely conclude both work correctly in isolation. The integration gap (forward-migration step 7 / step 7b bypassing the orchestrator while BD-108 exports it as the canonical entry point) is only visible when you compare the BD-108 surface against BD-108's own usage from its own forward-migration extension — exactly the cross-BD batch-level question.

### Finding F2
- **Severity:** MUST
- **Location:** `cross-BD` — `scripts/lib/tracker-promote.sh:621-655` (Path 1 tracker-mode side effects) and `tracker-promote.sh:833-933` (Path 2 tracker-mode side effects); compare V3.3-DELTA §3.3 line 152 + §3.4 (round-trip carriers); reverse path at `scripts/lib/tracker-migrate-reverse.sh:541` (Resolution emit reads parsed `.resolution` field which comes from `## Resolution` body section per line 417).
- **Title:** Path 1 / Path 2 forward does not sync Resolution text to tracker issue body → reverse migration loses Resolution for promoted-to TDs
- **Description:** V3.3 §3.3 explicitly names two carriers for round-trip safety: "BACKLOG entry's Resolution text (human-readable) and the `derived-from:` / `promoted-to:` label pair (queryable)." But Path 1's tracker-mode side effects (`tracker-promote.sh:621-655`) only call `provider_set_labels` (status:resolved + promoted-to:) and `provider_close` on the TD; they never `provider_update` (or equivalent) the TD issue body to add a `## Resolution` section with the `[YYYY-MM-DD, completed, promoted to phase-N]` text. The library returns `resolution_text` in the result JSON for PM Chat to apply to BACKLOG.md; PM Chat's BACKLOG.md is the flat-file truth — but in tracker mode, BACKLOG.md is a read-only mirror regenerated by reverse migration. So:
  1. User runs `pack td promote --to=phase-7 TD-031` in tracker mode → tracker has the new phase epic + label `derived-from:TD-031` + closed TD with `promoted-to:phase-7` label, but TD issue body is unchanged (no `## Resolution` section).
  2. User later runs `pack tracker disable` → `tracker-migrate-reverse.sh` reads each closed TD, extracts Resolution from the `## Resolution` body section (line 417 / `_tmr_extract_section "Resolution"`), finds nothing, emits `Resolved: n/a` to BACKLOG.md (line 543).
  3. Round-trip identity is broken — the human-readable Resolution carrier is lost.
- The `promoted-to:phase-N` label survives, but the V3.3 §3.3 "two carriers" contract is reduced to one. The `tracker_promote_reverse_path1` / `_path2` handlers at `tracker-promote.sh:1018, 1058` are diagnostic-only per BD-107 §13 limitation 3 — they don't reconstruct the BACKLOG; that's `tracker-migrate-reverse.sh`'s job, and reverse migrate has no awareness of `promoted-to:` labels (verified by grep — no hit in `tracker-migrate-reverse.sh`).
- **Suggested fix:** Two options. (a) Path 1 / Path 2 forward issues a `provider_update` (or backend equivalent) on the TD issue to insert/update a `## Resolution` body section with the Resolution text, mirroring the v10 lifecycle's existing `## Resolution` body convention; reverse migrate then reads it via the existing `_tmr_extract_section "Resolution"` path with no change. (b) Reverse migrate is extended to read the `promoted-to:` label and synthesize the Resolution text from it (`[<close-date>, completed, promoted to phase-N]`); requires close-date metadata, which GH issues carry as `closed_at`. Either fix preserves V3.3 §3.3 round-trip safety. (a) is more parallel to existing v10 mechanics; (b) is more compact. Recommend (b) as a follow-up BD with smaller surface; (a) if the maintainer prefers parallelism with v10. This batch ships with the gap; flag explicitly in BD-107 §13 limitations and the BD-110 `pack-auditor` agent's drift checks.
- **Source:** ARCHITECTURE-V3.3-DELTA.md §3.3 line 152 (round-trip carriers); §3.4 (Path 2 round-trip identical shape); `scripts/lib/tracker-migrate-reverse.sh:541` (reverse Resolution emit reads only parsed `.resolution`); `scripts/lib/tracker-promote.sh:1018-1052` (BD-107 §13 acknowledges reverse handlers are diagnostic-only).
- **Cross-cut?** **yes** — A per-BD reviewer for BD-107 would see the Path 1 / Path 2 forward orchestrators, the diagnostic-only reverse handlers, and the limitation note; they would not necessarily look at `tracker-migrate-reverse.sh` to discover that the reverse Resolution emit silently drops promoted-to TDs. ### Finding F4
- **Severity:** SHOULD
- **Location:** `scripts/lib/tracker-cycle-check.sh:30-37` (docstring claim) vs `scripts/lib/tracker-cycle-check.sh:200-273` (actual implementation) and ARCHITECTURE-V3.3-DELTA.md §5.5 line 290-291 (spec wording).
- **Title:** Cycle-check docstring claims to "match V3.3 §5.5 prose" but documents the opposite walk; spec wording itself is logically incorrect
- **Description:** ARCHITECTURE-V3.3-DELTA.md §5.5 line 290-291 says: *"the chat traverses `blocked-by` from the new edge's source for K hops; if the target appears in the closure, refuse the link."* The implementation walks from the proposed *target* (not source) and looks for the proposed *source* (not target). This opposite walk is **logically correct**: adding edge "X blocked-by Y" closes a cycle iff there's already a path Y → ... → X via blocked-by edges; the implementation walks from Y looking for X (correct), while the spec text would walk from X looking for Y (which detects the wrong condition — finding Y from X means X is already blocked by Y, which means the new edge is redundant, not a cycle). The cycle-check.sh docstring at lines 30-37 acknowledges this divergence but uses the misleading phrase "matches V3.3 §5.5 prose" before then describing the opposite walk. The implementation is correct; the spec is wrong; the docstring conflates the two. Tests 3.1-3.3 + 4.x in `test-tracker-cycle-check.sh` verify the correct semantics; the spec wording would fail these tests.
- **Suggested fix:** Either (a) update the docstring to say "the implementation INVERTS V3.3 §5.5's stated direction (which would not detect cycles correctly); the inversion is documented in V3.3 §5.5 line 290 as TODO-correct"; OR (b) update V3.3-DELTA §5.5 wording to match the implementation (the spec change is the smaller textual change since the algorithm is right). Recommend (b) as a PM-only architectural correction in a follow-up commit, mirroring the §6.R inline formalization pattern used at BD-106 land. The implementation correctness is not at risk for v11.0 ship; the docstring consistency should be fixed.
- **Source:** ARCHITECTURE-V3.3-DELTA.md §5.5 line 290-291; `scripts/lib/tracker-cycle-check.sh:30-37` (docstring); `scripts/lib/tracker-cycle-check.sh:200-273` (correct implementation); `scripts/tests/test-tracker-cycle-check.sh:177-188, 190-200` (correct-semantic tests).

Per-BD reviewer would more likely propose option (a) only.
