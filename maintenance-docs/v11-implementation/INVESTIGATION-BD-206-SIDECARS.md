## Q2 — Why does only `changelog/` have `_format.md`?

**Fact:** it is a deliberately-documented *"project-side asymmetry."* The
changelog has a distinct entry shape that the other streams don't:
date-slug filenames (`YYYY-MM-DD-<slug>.md`), append-only ordering, version/phase
heading grammar, deterministic `---` separator emission, and a filename→heading
slug mapping. BD-167 carved that into a dedicated `_format.md`. The backlog and
implementation-plan entry formats are simpler and were folded into each stream's
`_rules.md` ("Entry contract" section). The **pack-side changelog has no
`_format.md` analog** (README line 149; `_format.md`'s own header says so).

**Important nuance (bears on Q4):** the current `_format.md` is **not purely a
"format" doc** — it mixes a format spec (entry shape, filename mapping) WITH
operational **rules** (append-only; one-entry-per-phase; date = merge-to-main
date; mark resolved TD ✅ in the same commit; update README Known Limitations).
Under your corrected model, those rules belong in `_rules.md`.

## Q3 — How do we guarantee architects/planners won't anchor on the `_rules.md` content?

**First, the evidence for *why* this matters — the current sidecars embody a
SUPERSEDED model that conflicts with your corrected one on 4 axes:**

1. **`_intro.md` role is INVERTED.** Current = a *generated, do-not-edit mirror*.
   Your corrected model = a *hand-editable, human-only intro*. Opposite purposes.
2. **`_rules.md` mutability is CONTRADICTORY.** The file says "immutable," but
   `init-project.sh` (~line 1012) preserves a *"customized `_rules.md` … with the
   pack version written as a `.pack-template` sidecar for manual reconcile."* —
   i.e. the current machinery EXPECTS clients to customize `_rules.md`. Your
   corrected model = `_rules.md` MUST NOT be modified.
3. **The entry schema is the OLD one.** `_rules.md` "Entry contract" =
   *"one v10-grammar TD entry per file, byte-additive on the legacy monolithic."*
   BD-206 replaces this with **form families** — a different schema.
4. **Overlapping mirror concepts.** Both `_intro.md` (regenerated readable view)
   AND a monolith `docs/project/BACKLOG.md` ("regenerated mirror … never source of
   truth") exist. BD-206's no-monolith-mirror + your corrected `_intro.md` role
   collapse this muddle.

An architect that treats these files as a starting point inherits all four
defects. So anchoring isn't a style risk — it would re-import the rejected model.

**Mechanisms available to guarantee non-anchoring (orchestration — Pack Chat's
lane). These are established pack practices:**

- **M1 — Withhold the content entirely.** Do NOT put the current sidecars'
  *content* in any architect/planner prompt. Give only their *paths + the fact
  that they are SUPERSEDED and slated for full replacement*. (Mirrors how the
  rejected design chain is quarantined and unreadable.)
- **M2 — Derive the target from the corrected requirements, not the artifacts.**
  The architect designs the target sidecars from your stated model
  (`DECISIONS-BD-206-RESTART.md` §1–§3) + first principles + the OT gold schema —
  never from the current files.
- **M3 — Separate "what exists (to delete)" from "what to build."** The current
  files are an input only to the *migration/cleanup* step (what gets removed),
  never to the *target* design.
- **M4 — Choose the reference model deliberately.** If a reference is wanted, the
  pack-side per-entry trees (`/backlog/`, `/changelog/`) are closer to correct —
  BUT they may carry the same `_intro.md`-as-mirror assumption, so even they are
  not a safe "copy this." Safest reference = your corrected model text.
- **M5 — Explicit prompt directive + verification.** State in the prompt: "the
  current project-template sidecars are superseded; their content is NOT correct,
  NOT a starting point, NOT locked." Require the architect's output to show it
  derived the target from the corrected requirements (the Rules-Applied block can
  carry this attestation).
- **M6 — Fresh instance.** A fresh architect (no exposure to the rejected design)
  per the restart.

This directly satisfies your constraint #6 (M1 + M5).
