# V11.1 Discussion — GitHub Projects integration

**Status:** Parking-lot discussion for v11.1 planning. Not v11.0 scope.
**Date of discussion:** 2026-05-20.
**Context:** Pack Chat (main / v10.1) session, captured for v11.1 planning while v11-dev was mid-flight on per-entry flat-file architecture work.

---

## 1. Scope of this doc

Captures a design discussion about whether and how the pack should integrate GitHub Projects (Projects v2) into v11+ workflows. Includes:

- What GitHub Projects are and how they relate to GitHub Issues
- Where they overlap with what the pack already does
- Whether they complement or compete with the pack
- Granularity questions: phase-level vs grouping-level Projects
- Grouping models (user journeys, ambient/foundational, other) and how to express them without polluting phase entries
- v11.0-agnostic design constraint
- Proposed v11.1 scope shape

The discussion does not propose any v11.0 work. The grouping doc concept and tracker integration both layer on top of the v11.0 per-entry shape without changing it.

---

## 2. What GitHub Projects are

GitHub Projects (current generation, sometimes called Projects v2) is a **project-management view layer that sits above Issues and PRs**. It lives at user, organization, or repo scope and aggregates items from across repos in the same org.

Key features:

- **Multi-view:** Board (kanban), Table (spreadsheet-like), Roadmap (timeline / Gantt-ish)
- **Custom fields per project:** Status, Iteration, Priority, Estimate, plus arbitrary single-select / text / number / date / iteration fields you define
- **Items can be Issues, PRs, or Drafts** — Drafts are project-local items that haven't been promoted to issues yet
- **Workflows / automations:** auto-add new items by criteria; auto-set Status when an issue closes or a PR merges
- **Insights:** built-in charts (status histogram, burnup, group-by-field counts)

Projects don't replace Issues; they **organize them**. A Project item that came from an issue is *still* the issue — same number, same labels, same comments, same body. The Project adds project-scoped fields on top, visible from the issue page in a "Projects" sidebar. One issue can live in multiple Projects with different field values per Project.

Layering:

- **Issues** — the durable artifact (body, comments, labels, state)
- **Projects** — curated views of issues with extra ad-hoc fields for planning

Removing an issue from a Project doesn't change the issue. Closing an issue is seen by the Project and can trigger an automation.

## 3. Overlap with what the pack already does

The pack's v11 tracker already produces structured GitHub Issues from `BACKLOG.md` entries:

- Labels for type (`bd-v11.0`, `td-v11.0`), status (`status:open`, `status:resolved`), category
- Structured body sections (Title, Type, Status, Blockers, Unblocks, File/Symbol, Description, Resolved)
- HTML-comment markers (`template_version`, `pack-id`)
- Sub-issue dependencies (planned via BD-111)

Mapping to Projects:

| Pack concept | Project equivalent |
|---|---|
| BACKLOG entry | Item (issue with project fields) |
| Status field in entry body | Project Status field (or driven from labels) |
| Type / Severity | Project single-select fields |
| Blockers / Unblocks | Projects has no native blocked-by; would be a custom field or external linking |
| IMPLEMENTATION-PLAN phases | Project Iteration field, or grouped Board view |
| STATUS.md dashboard | Project Board view (kanban) or Table view |
| pack-tracker mirror | (nothing equivalent — Projects is read-online, not file-based) |

---

## 4. Complement or compete?

**Mostly complement.** Three reasons:

1. **Different audiences.** The pack's value proposition is *agent-friendly, deterministic, multi-provider, CLI-driven*. Projects' value proposition is *human-friendly, visual, GitHub-specific, web-driven*. Different value systems — the pack will never want Projects as its agent-facing surface, but humans browsing pack-managed issues benefit from a Projects view.
2. **Different layers.** Projects organizes issues; the pack creates and maintains them. They stack rather than collide. You can point a Project at the pack-created issues today without touching pack code — and get a Board view for free.
3. **One real overlap zone — the STATUS dashboard.** Projects' Board view does much of what STATUS.md does (current phase, phase table, throughput). In tracker mode, STATUS.md becomes somewhat redundant if a Project is also in use. But STATUS.md still earns its keep when tracker mode is off; Projects don't help flat-file mode at all.

Areas of genuine potential competition / duplication:

- **Custom fields vs. entry-body sections.** Putting Severity / Priority / Estimate in BOTH Project custom fields AND the BACKLOG entry body creates two sources of truth.
- **Iteration tracking vs. IMPLEMENTATION-PLAN phases.** Same drift risk. Either Phase-from-plan drives the Iteration field, or Iteration becomes purely project-scoped UI noise.
- **GH-specific.** Pack's TrackerProvider abstraction targets multiple backends. Projects is GitHub-only. Any first-class pack support for Projects breaks the multi-provider posture unless conditionalized as a GH-specific feature.

## 5. Three integration shapes (lightest to heaviest)

- **Shape 0 — Do nothing in the pack.** Users opt into Projects independently. Point an org-level Project at the pack-created issues; configure custom fields manually; get a Board view. Pack code doesn't know Projects exists. Works today; zero pack cost.
- **Shape 1 — Lightweight Project hints in tracker config.** Add an optional `tracker.toml` `[project]` section (project number / URL / default-field-map). `pack tracker init` adds issues to the named Project, optionally populating Status / Iteration from BACKLOG state. Pack stays multi-provider-compatible (the section is opt-in and GH-only).
- **Shape 2 — First-class Project integration as a tracker-mode surface.** Pack creates and maintains the Project alongside Issues. STATUS.md becomes a Project Board view URL when tracker is on. Project fields become a documented part of the v11 form-family. Tightly couples the pack to GH and creates dual-state-management complexity.

**Working assumption:** Shape 0 is the default today. Shape 1 is the candidate for v11.1. Shape 2 is probably not worth doing.

## 6. Version targeting — v11.1, not v12

The pack's versioning convention:

- Minor versions (vN.0, vN.1, …) mark incremental improvements — doc updates, new templates, prompt and workflow refinements
- Major versions mark large additions or breaking changes

Shape 1 is incremental: opt-in `tracker.toml` section + trigger logic in `pack tracker init` + optional field-map. No breaking changes, no schema migrations, no agent-roster impact. Fits the minor-version definition. **v11.1 is the right slot, not v12.**

## 7. Are phases enough for a Project?

**No. Phases are too small.**

Phase sizing in v11 IMPLEMENTATION-PLAN is 1 to ~10 tasks per phase. A Project with 10 items doesn't earn the UX overhead of Project creation, configuration, custom-field setup, and ongoing maintenance:

- Board view: 5–10 cards across 3–4 columns is sparse
- Insights tab: 7 data points is noise
- Custom fields, automations, workflows: overkill for one phase

So Phase-as-Project is the wrong granularity. **Project = collection of phases** is the right granularity. A grouping that spans 4–6 phases (each with 3–8 tasks) gives a Project of 20–40 items — the right shape for the UX to pay off.

Adjacent alternative: a single all-phases Project, sliced by Iteration field, where each Phase ID becomes an Iteration. Sprint-board-style temporal view. This doesn't conflict with grouping projects — both can coexist (one issue can live in multiple Projects).

## 8. Groupings — the real design space

Multiple grouping kinds, not just user journeys:

- **User journeys (user-facing):** Authentication, billing, onboarding, etc.
- **Ambient / non-user-facing features:** observability, telemetry, security hardening
- **Foundational batches:** platform work, tech-debt removal, refactor clusters
- **Release packages:** what ships together in a specific minor or major
- **Others:** team-specific groupings (e.g., performance, accessibility, compliance)

A grouping is a **named collection of phase IDs that share a common purpose.** The purpose is human-judgment, not derivable from the codebase alone.

### Why phases run in different order than journey logic

Phases execute in technical-dependency order (Blockers / Unblocks resolve to a DAG). A user journey's UX-presentation order (login → signup, even if signup is technically simpler) may not align. The pack should not try to reconcile these two orderings:

- **Execution order:** driven by the Blockers / Unblocks DAG. Pack manages this.
- **UX presentation order:** belongs in the PRD or journeys doc. Not the pack's concern.

A grouping doc enumerates *membership* (which phases are part of this grouping), not *execution sequence*. The Project shows the phases as a member list; the team handles UX sequencing separately.

### Deduplication when phases overlap groupings

Concern: "the batch of phases that make up a complete user journey, minus the ones already completed by another user journey's work."

Handled automatically by GitHub Projects semantics:

- A phase = one issue
- The issue lives as multiple Project items (one per grouping that includes it)
- Closing the issue once propagates to all Projects
- Each Project's progress = (closed member items) / (total member items)

If Phase 2.3 belongs to Journey A and Journey B, closing Phase 2.3 advances both. No deduplication logic needed in the pack.

## 9. Tagging vs. heuristic vs. explicit-membership

Three approaches to capturing grouping membership:

### Tagging on the phase

Each phase carries `Groupings: [auth-journey, foundational-platform]` or similar field.

- **Pro:** O(1) lookup, unambiguous
- **Con:** A phase serving multiple groupings can't have one "owner" tag without ambiguity
- **Con:** Drift when grouping membership changes
- **Con:** Phases conflate execution metadata (Blockers, File/Symbol) with planning metadata (which group am I in?)
- **Con:** "What new grouping can I make from existing phases?" requires retagging multiple phases

### Heuristic / topology-based

Compute grouping membership at query time from phase content (title, description, file/symbol, dependency-graph topology).

- **Pro:** No phase changes; flexible
- **Pro:** New groupings don't require touching phases
- **Con:** Fuzzy; ambiguous boundary cases
- **Con:** Inscrutable — hard to predict which phases land in which grouping
- **Con:** Computed grouping drifts as the codebase shifts

### Explicit membership in the grouping doc (recommended)

Groupings live in their own docs. Each grouping doc declares membership by reference to phase IDs. The phase itself doesn't know it's part of any grouping; the grouping knows it includes the phase. Same pattern the pack already uses for `Blockers / Unblocks` — the reference lives in the citing entry, not as a tag on the cited target.

- **Pro:** Phases stay agnostic (no tags, no grouping metadata)
- **Pro:** One phase can belong to multiple groupings (each declares it independently)
- **Pro:** Grouping membership can be revised without touching any phase
- **Pro:** Deterministic — no fuzzy matching
- **Pro:** v11.0-agnostic — phases ship without grouping awareness; groupings layer on later
- **Con:** Some manual curation needed to define groupings (appropriate — this IS human judgment work)

**Decision: explicit-membership wins.** Tagging is brittle; heuristics are fuzzy; explicit membership is the cleanest fit with the pack's existing reference-by-ID patterns.

### Hybrid where it earns its keep

If a class of phases is consistently used in one kind of grouping (e.g., always foundational-platform), the *grouping doc* can declare "auto-include phases matching X regex" as a convenience layer. That's a feature of the grouping doc, not a tag on the phase. The phase stays clean. Sparingly used.

## 10. Proposed grouping doc shape

Lightweight, declarative. One file per grouping. In a `groupings/` directory parallel to the per-entry pattern (parallel to `backlog/`, `implementation-plan/`, `changelog/`).

```markdown
# Grouping: Auth & Identity (user-journey)

**Kind:** user-journey
**Description:** End-to-end authentication and identity flows — signup,
login, MFA, account recovery, session management.

**Member phases (by ID):**
- phase-2.1 — Auth schema migration
- phase-2.3 — OAuth provider integration
- phase-3.4 — Session storage refactor
- phase-4.1 — MFA flow
- phase-4.2 — Account recovery email

**Source PRD section / journeys doc:** `docs/project/JOURNEYS.md § Auth`
(optional reference if a PRD or journeys doc exists)
```

Three properties of this shape:

- **Kind is enumerated, not free-form.** `user-journey`, `ambient-feature`, `foundational-batch`, `refactor-cluster`, `release-package` — pack ships a default enum; users extend if needed. The Kind is the *one* tagging-shaped element, but it's on the grouping, not on the phase. Each Kind affects how the grouping renders and what default Project fields it gets.
- **Member-list is just IDs.** No reordering, no annotation, no execution-sequence metadata. Execution order is determined by phase Blockers; UX-presentation order is outside the pack.
- **PRD reference is optional.** Some teams have a PRD with journeys; some have a separate journeys doc; some have neither. The pack does not parse the PRD or journeys doc; the grouping doc cites it for human context.

## 11. PRD / JOURNEYS.md considerations

PRDs vary widely. Some have user journeys, some have personas, some have use cases, some are just feature lists. The pack should not require a particular PRD format.

Right separation:

- **Grouping doc** — pack-readable, the authoritative source for "which phases are in which grouping"
- **PRD / JOURNEYS.md** — user's choice of format, content, and structure. Pack does not parse.

This means:

- Teams with no PRD can still use groupings (foundational batches, refactor clusters work without any PRD)
- Teams with a PRD that has journeys can write groupings that reference the PRD
- Teams with a separate JOURNEYS.md can do the same
- Teams with custom doc structures can adapt the grouping doc to point at whatever they have

The pack stays out of the PRD-format debate. The grouping doc is the single integration point.

## 12. v11.0 impact: zero

Critical constraint from the discussion: **groupings must be agnostic of v11.0 work and easily applied after v11.0 lands.**

This is satisfied by the explicit-membership design:

- Phases ship in v11.0 with no grouping awareness (no new fields, no tags, no metadata)
- Per-entry shape stays exactly as the v11.0 architect designs it
- `implementation-plan/phase-NN.md` stays grouping-agnostic
- `backlog/BD-NNN.md` (or `TD-NNN.md`) stays grouping-agnostic
- `tracker.toml`, `pack-tracker.sh`, and the migrator stages do not change in v11.0 for grouping support

The grouping layer adds in v11.1+ as a clean overlay:

- New `groupings/` directory under `docs/project/` (client) or repo root (pack, if needed)
- `groupings/_rules.md` defines the doc shape (extends the per-entry pattern)
- Optional `[grouping]` section in `tracker.toml`
- `pack tracker init` extension to read groupings and create Projects

## 14. Open questions for v11.1 planning

Items the discussion did not resolve. The v11.1 planner / architect should pick these up:

1. **Groupings directory location for pack-self.** Pack-self uses BACKLOG + CHANGELOG only (no IMPLEMENTATION-PLAN, no STATUS, per the per-entry architecture decision). Does pack-self even *have* phases that would benefit from grouping? If pack development doesn't use phase decomposition (it uses BD numbering + batch grouping in EXECUTION-PLAN), the pack-self grouping use case is different from the client use case. Possible answer: groupings are client-side only.
2. **Kind enumeration extensibility.** Pack ships a default Kind enum. Should users be able to extend it, and if so, how is the extension validated? Or is the enum fixed?
3. **Project-creation API costs.** GitHub Projects creation is API-cost-bearing. `pack tracker init` already makes many API calls; adding Project creation per grouping could push past rate limits. Mitigation: incremental creation (one Project at a time, with state checkpoints), opt-out for users who'd rather create Projects manually.
4. **Sync direction for Project fields.** If a user edits a Project field in the GitHub UI (e.g., changes Status), does the pack overwrite it on next mirror sync, or treat it as authoritative and pull it back into the BACKLOG entry? The pack's existing pattern is "GH issue is source of truth, mirror file is local cache" — Projects sit above issues, so Project field edits don't automatically flow into the issue body. Decision needed.
5. **Multi-Project membership cost.** A phase in 3 groupings = 3 Project items to maintain. Closing the issue propagates automatically (good). Changing the issue body propagates automatically (good). But Project field edits are per-Project — does each Project need its own field-map config in `tracker.toml`? Likely yes; structure TBD.
6. **Should groupings be in the RAG manifest?** Like `_rules.md` and METHODOLOGY.md, grouping docs are operational reference material. If the user is at PM Chat asking "what phases are part of the Auth journey?", reading the grouping doc directly is fastest. RAG ingestion of grouping docs is plausible but not essential.
7. **Provider abstraction implications.** Projects is GH-specific. If a Forgejo / Linear / Jira backend lands later, what's the analogous concept? Linear has Projects (similar). Jira has Epics + Sprints (different shape). Forgejo has nothing equivalent. The grouping doc format should be provider-agnostic; the *tracker integration* of groupings should be per-provider.

## 15. Working assumptions parking lot

Held over for v11.1 planning to confirm or revise:

- Shape 1 is the integration choice (not Shape 2)
- v11.1 minor, not v12 major
- Phase-as-Project is rejected; Grouping-as-Project is the granularity
- Explicit-membership in grouping docs (not phase tags, not heuristics)
- Phases stay agnostic of grouping membership
- PRD / JOURNEYS.md format is user's choice; pack does not parse
- GitHub Projects' multi-Project-per-issue semantics handles overlap dedup automatically
- v11.0 ships without any grouping-related code or doc changes
- Grouping layer is a v11.1 add-on
