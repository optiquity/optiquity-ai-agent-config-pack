# Schema — `phase-epic-v11.0` (phase epic)

This document fixes the on-tracker representation of a phase epic at
template version `phase-epic-v11.0`. Phase epics are the L1 anchor for
implementation phases. Day-to-day, phase epics are created
**programmatically** by Pack Chat / PM Chat at migration time or when
introducing a new phase — not by user form. The `phase-epic-skeleton`
option in `work-item.yml` exists as a rare-case fallback.

Reference: ARCHITECTURE.md §4.5, ARCHITECTURE-V3.3-DELTA.md §2.5 / §6.3
/ §6.4 / §6.5, IMPLEMENTATION-PLAN.md BD-064 + Addendum 4 §2.2.

## 1. Identifier scheme

- Identifier: `phase-N`, where N is the integer phase number from
  IMPLEMENTATION-PLAN.md.
- Uniqueness scope: per project. One phase epic per phase number.
- Identity owner: pack (IMPLEMENTATION-PLAN.md authoritative).
- Round-trip carrier: title prefix `Phase N — <phase title>` plus
  body marker `<!-- pack-id: phase-N -->`.

## 2. Body marker trio

```
<!-- pack-id: phase-N -->
<!-- template_version: phase-epic-v11.0 -->
<!-- pack-version: v11 -->
```

When created via `provider.create()` (the day-to-day path), the
markers are written directly with the resolved values. When created
via the rare `wi-type=phase-epic-skeleton` form path, chat triage
rewrites the markers from `PENDING` / `work-item-v11.0` to the
specific values based on `wi-phase-number`.

## 3. Label family

| Label | Source | Notes |
|---|---|---|
| `phase-epic` | chat / programmatic create | provenance; never removed |
| `phase-N` | chat / programmatic create | self-membership; never removed |
| `template:phase-epic-v11.0` | chat / programmatic create | updated by `pack tracker update-templates` |
| `derived-from:TD-NNN` | chat (TD-promotion path 1) | optional; one or more |
| `status:*` | chat | mirrors phase epic state; see V3.3 §6.3 |

Phase epics open when the phase begins and close (by chat) when all
sub-issue phase tasks are closed.

State mapping per V3.3 §6.3:

| Phase epic state | tracker state | `state_reason` |
|---|---|---|
| Open (phase active) | open | — |
| Closed (phase complete: all tasks done) | closed | `completed` |

## 4. Body section grammar

The phase epic body is brief — the bulk of phase content lives in
IMPLEMENTATION-PLAN.md and in the sub-issue phase tasks. The body
contains the phase summary plus an anchor line back to the plan:

```
<!-- pack-id: phase-N -->
<!-- template_version: phase-epic-v11.0 -->
<!-- pack-version: v11 -->

## Phase summary

<one-paragraph summary of the phase's purpose, copied from
IMPLEMENTATION-PLAN.md `### Phase N — <title>` heading paragraph>

## Plan anchor

IMPLEMENTATION-PLAN.md `### Phase N — <title>`

## Tasks

<auto-generated by chat: bullet list of phase-task issues (linked
via sub-issue parent or label fallback). Updated when phase tasks
are added, removed, or change state.>
```

The Tasks section is regenerated by chat on every phase-task state
change. Manual edits to that section are overwritten.

## 5. Sub-issue / hierarchy

Phase tasks are children of the phase epic via:
- **First-class sub-issue parent** when `hierarchy.supported = true`
  in the backend's capability flags (V1 §2.7.2 — github supports this).
- **Label fallback** `parent:phase-N` on each task otherwise (V3.2 §2.7).

The pack does not store the child list in the phase epic body; it is
derived at read time via `provider.sub_issue_list(phase-N)` (or label
query in the fallback case).

## 6. Reverse-emit grammar

Reverse migration emits the phase epic as the v10 IMPLEMENTATION_PLAN.md
heading + summary paragraph:

```
### Phase N — <title>

<Phase summary section content>

(Tasks emitted as #### N.M sub-headings — see phase-task-v11.0/SCHEMA.md.)
```

The plan-anchor line is dropped on reverse (it would self-reference
the file being written). The Tasks list is regenerated from the
phase-task issues on reverse-emit, not from the phase epic body.

`derived-from:TD-NNN` labels become a footer line per phase:

```
<!-- derived-from: TD-NNN, TD-NNN, ... -->
```

For round-trip preservation per V1 §6.0.

Tracker-only enrichment (status comments, milestone associations) is
preserved in the reverse-migration sidecar per V1 §6.6.1.
