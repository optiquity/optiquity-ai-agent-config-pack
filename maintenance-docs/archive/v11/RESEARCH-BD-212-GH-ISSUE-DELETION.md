## §1. The deletion API surface

### 1.1 GraphQL `deleteIssue` — live schema introspection (production endpoint, no preview headers, this account's token)

Command + verbatim output (2026-06-11):

```
$ gh api graphql -f query='query { __type(name: "DeleteIssueInput") { name description inputFields { name description type { name kind ofType { name kind } } } } }'
{"data":{"__type":{"name":"DeleteIssueInput","description":"Autogenerated input type of DeleteIssue","inputFields":[{"name":"clientMutationId","description":"A unique identifier for the client performing the mutation.","type":{"name":"String","kind":"SCALAR","ofType":null}},{"name":"issueId","description":"The ID of the issue to delete.","type":{"name":null,"kind":"NON_NULL","ofType":{"name":"ID","kind":"SCALAR"}}}]}}}
```

```
$ gh api graphql -f query='query { __type(name: "DeleteIssuePayload") { name description fields { name description type { name kind ofType { name kind } } } } }'
{"data":{"__type":{"name":"DeleteIssuePayload","description":"Autogenerated return type of DeleteIssue.","fields":[{"name":"clientMutationId","description":"A unique identifier for the client performing the mutation.","type":{"name":"String","kind":"SCALAR","ofType":null}},{"name":"repository","description":"The repository the issue belonged to","type":{"name":"Repository","kind":"OBJECT","ofType":null}}]}}}
```

```
$ gh api graphql -f query='query { __type(name: "Mutation") { fields { name description } } }' --jq '.data.__type.fields[] | select(.name == "deleteIssue")'
{"description":"Deletes an Issue object.","name":"deleteIssue"}

$ gh api graphql -f query='query { __type(name: "Mutation") { fields { name args { name type { name kind ofType { name kind } } } } } }' --jq '.data.__type.fields[] | select(.name == "deleteIssue")'
{"args":[{"name":"input","type":{"kind":"NON_NULL","name":null,"ofType":{"kind":"INPUT_OBJECT","name":"DeleteIssueInput"}}}],"name":"deleteIssue"}
```

**Verified shape:**
- Mutation: `deleteIssue(input: DeleteIssueInput!): DeleteIssuePayload` — "Deletes an Issue object."
- Input: `issueId: ID!` (the issue NODE ID, not the issue number) + optional `clientMutationId: String`.
- Payload: `repository: Repository` ("The repository the issue belonged to") + optional `clientMutationId`. The payload does NOT echo the deleted issue (it no longer exists) — success is detectable by a non-error response; the `repository` field is the only data anchor.
- Consequence for the verb: a delete loop must first resolve issue number → node ID (e.g., `repository.issue(number:).id`), then mutate by node ID.

Docs reference for the same mutation: https://docs.github.com/en/graphql/reference/mutations#deleteissue (retrieved 2026-06-11; the docs page is client-rendered so the section text was not extractable by GET — the live introspection above is the authoritative evidence and is STRONGER: it proves the mutation is in the production schema visible to this exact token).

## §2. Permission requirements

### 2.1 Role requirements — official docs (retrieved 2026-06-11)

Source: https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/deleting-an-issue — quoted verbatim from the fetched page text:

> "People with admin permissions in a repository can permanently delete an issue from a repository."
>
> "The ability to delete issues depends on whether the repository is owned by a personal account or an organization: **The only account that can delete issues in a repository owned by a personal account is that account.** Only accounts with admin or owner permissions can delete issues in a repository owned by an organization. To delete an issue in a repository owned by an organization, an organization owner must enable deleting issues for the organization's repositories."

Personal vs org difference (load-bearing for the capability contract):
- **Personal repo (the BD-212 target):** ONLY the owning account can delete — even collaborators granted admin-equivalent access on a personal repo cannot. The pack's account IS the owner of its repos, so deletion is available.
- **Org repo:** admin/owner role AND an org-level opt-in setting. Source: https://docs.github.com/en/organizations/managing-organization-settings/allowing-people-to-delete-issues-in-your-organization (retrieved 2026-06-11), quoted: "**By default, issues cannot be deleted in an organization's repositories.** An organization owner must enable this feature for all of the organization's repositories first. Once enabled, organization owners and people with admin access in an organization-owned repository can delete issues." — i.e. on an org repo, an admin-role preflight is NECESSARY but NOT SUFFICIENT; the org toggle is a second, API-invisible-until-tried gate. The verb's permission preflight must therefore treat "role check passed" as advisory and still classify a FORBIDDEN-class mutation error as terminal (§6).

### 2.2 Token requirements

**Classic scopes (the actual target token model):** source https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps (retrieved 2026-06-11), quoted: "`repo` — Grants full access to public and private repositories including read and write access to code, commit statuses, repository invitations, collaborators, deployment statuses, and repository webhooks." Issues read/write on private repos rides on `repo`. The docs do not name a delete-issue-specific scope; no scope finer than `repo` exists for private-repo issue writes in the classic model. The target token HAS `repo` (verified, §0). The limiting factor is the ROLE (§2.1), not the scope. There is no documented per-mutation scope table for GraphQL; classic-token GraphQL access follows the same scopes — DOCUMENTED-SILENT on a deleteIssue-specific scope line, resolved empirically by probe P3 (§8).

**Fine-grained PATs (NOT the target's token, recorded for the capability contract):**
- Fine-grained PATs can call the GraphQL API since 2023-04-27. Source: https://github.blog/changelog/2023-04-27-graphql-improvements-for-fine-grained-pats-and-github-apps/ (retrieved 2026-06-11).
- Fine-grained PATs are GA since 2025-03-18. Source: https://github.blog/changelog/2025-03-18-fine-grained-pats-are-now-generally-available/ (retrieved 2026-06-11).
- The official per-operation permission mapping ("Permissions required for fine-grained personal access tokens") covers REST endpoints only; since there is no REST delete-issue endpoint (§1.2), there is NO documented fine-grained permission line for `deleteIssue`. The REST Issues GET endpoint's embedded progAccess metadata (extracted from the REST docs page, 2026-06-11) shows `"fineGrainedPat":true,"permissions":[{"\"Issues\" repository permissions":"read"}]` for reads; the corresponding write permission is "Issues: write", but whether "Issues: write" + owner role suffices for `deleteIssue` under a fine-grained PAT is **DOCUMENTED-SILENT**. Design consequence: the verb must NOT assume fine-grained-PAT compatibility; the documented-verified path is classic-scope `repo` + owner/admin role. If a future probe wants fine-grained coverage, that is a separate probe leg — not required for BD-212 (target uses classic scopes).

## §5. Rate / abuse limits, and the BD-103 100ms throttle assessed

All quotes retrieved 2026-06-11 from https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api unless noted.

1. **Primary GraphQL limit:** "For users: 5,000 points per hour per user. This includes requests made with a personal access token..." (a simple mutation costs at most its node cost; 211 deletes are far below 5,000/hr).
2. **Secondary limits (verbatim, the complete relevant set):**
   - "Make too many concurrent requests. No more than 100 concurrent requests are allowed. This limit is shared across the REST API and GraphQL API."
   - "Make too many requests to a single endpoint per minute. No more than 900 points per minute are allowed for REST API endpoints, and no more than 2,000 points per minute are allowed for the GraphQL API endpoint."
   - "Create too much content on GitHub in a short amount of time. In general, no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour are allowed. Some endpoints have lower content creation limits. Content creation limits include actions taken on the GitHub web interface as well as via the REST API and GraphQL API."
   - "No more than 90 seconds of CPU time per 60 seconds of real time is allowed. No more than 60 seconds of this CPU time may be for the GraphQL API."
   - Point costs: "GraphQL requests without mutations — 1. GraphQL requests with mutations — 5."
3. **Do the 80/min + 500/hr content limits apply to DELETIONS?** The documented trigger is "Create too much content" / "content-generating requests". A deletion is not content creation, and the docs do NOT enumerate which operations count — **DOCUMENTED-SILENT** for deletes. The docs also warn: "These secondary rate limits are subject to change without notice. You may also encounter a secondary rate limit for undisclosed reasons." Design must therefore treat 80/min-500/hr as POSSIBLY applying and stay under them anyway (a compliant pacing is free — see below).
4. **Documented pacing guidance (the controlling rule):** GraphQL doc, "Staying under the rate limit": "To avoid exceeding a rate limit, you should **pause at least 1 second between mutative requests** and avoid concurrent requests." Identically in REST best practices (https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api, 2026-06-11): "If you are making a large number of POST, PATCH, PUT, or DELETE requests, wait at least one second between each request."
5. **Documented retry behavior on a limit hit:** "If you exceed a secondary rate limit, the response status will be 200 or 403, and you will receive an error message that indicates that you hit a secondary rate limit. If the `retry-after` response header is present, you should not retry your request until after that many seconds has elapsed. If the `x-ratelimit-remaining` header is 0, you should not retry your request until after the time, in UTC epoch seconds, specified by the `x-ratelimit-reset` header. Otherwise, wait for at least one minute before retrying. If your request continues to fail due to a secondary rate limit, wait for an exponentially increasing amount of time between retries... Continuing to make requests while you are rate limited may result in the banning of your integration."

**BD-103 100ms-throttle assessment: NON-COMPLIANT with documented guidance.** 100ms = 10 mutations/s = 600/min. That (a) violates the explicit "pause at least 1 second between mutative requests"; (b) at 5 points/mutation = 3,000 points/min, EXCEEDS the 2,000 points/min GraphQL secondary limit; (c) if deletes count as content-generating, 600/min is 7.5× the 80/min limit. **Required pacing: ≥1,000ms between delete mutations, serial (no concurrency), honoring `retry-after`/`x-ratelimit-reset` on any limit response, with exponential backoff on repeat** — exactly matching the BD-212 charter's "≥ the provider's min-write interval; honor retry-after." A 211-issue reset at 1s pacing ≈ 3.5–4 minutes wall clock; ~60 mutations/min = 300 GraphQL points/min (< 2,000), ≤ 60 content-ops/min (< 80), 211/hr (< 500), 1,055 primary points (< 5,000/hr). Compliant on every documented axis.

## §6. Failure modes and machine classification

GitHub GraphQL errors carry a typed `type` field in each `errors[]` entry — classification does NOT require message string-matching. Empirical capture (read-only query, 2026-06-11, this token):

```
$ gh api graphql -f query='query { repository(owner: "DShaneNYC", name: "definitely-nonexistent-repo-xyz-12345") { id } }'
{"data":{"repository":null},"errors":[{"type":"NOT_FOUND","path":["repository"],"locations":[{"line":1,"column":9}],"message":"Could not resolve to a Repository with the name 'DShaneNYC/definitely-nonexistent-repo-xyz-12345'."}]}
EXIT: 1
```

Observed contract: HTTP 200 + `data` with `null` at the failed path + `errors[]` with `type`, `path`, `locations`, `message`. `gh api graphql` exits non-zero when `errors[]` is present (exit 1 above) — usable as the shell-level failure signal, with `jq '.errors[].type'` for the class.

| Failure | Expected signal | Status |
|---|---|---|
| Issue node ID does not exist / already deleted | `errors[].type == "NOT_FOUND"` (the NOT_FOUND shape is empirically captured above for a missing node; the deleteIssue-specific instance is probe P6) | Empirical (shape) + probe P6 (mutation-specific) |
| Insufficient role (non-admin token/actor) | Expected `errors[].type == "FORBIDDEN"` — **DOCUMENTED-SILENT** (no official per-mutation error table exists); the GraphQL docs do not enumerate mutation error types | DOCUMENTED-SILENT → probe P9 (only if a non-admin credential is available; otherwise recorded as untestable-on-target, since the target account is owner everywhere it operates) |
| Missing token scope | `INSUFFICIENT_SCOPES` error type is well-known but not officially tabled | DOCUMENTED-SILENT; not design-load-bearing (target token has `repo`) |
| Secondary rate limit hit | "response status will be 200 or 403" + error message indicating secondary rate limit + `retry-after` header when present (§5.5 quote) | DOCUMENTED |
| Primary rate limit exhausted | HTTP 200, error message, `x-ratelimit-remaining: 0`, retry after `x-ratelimit-reset` (GraphQL rate-limits doc, 2026-06-11) | DOCUMENTED |
| Issue transferred before delete | Transfer changes the repo home; REST Get returns `301 Moved Permanently` for transferred issues (Get-an-issue doc, §4) — the stale node ID's behavior under deleteIssue is DOCUMENTED-SILENT | DOCUMENTED-SILENT → probe P6-adjacent; verb should re-resolve node IDs immediately before deleting (TOCTOU window noted for the architect) |
| Issue locked | No documented interaction between lock state and deletion | DOCUMENTED-SILENT → probe P3 may use one locked pack-marked issue to close this cheaply |

**Classifier recommendation for the architect:** branch on (`gh api` exit code, `errors[0].type`) — `NOT_FOUND` → treat-as-already-deleted (idempotent success for a reset loop); `FORBIDDEN`-class → terminal fail-loud (admin preflight lied or org toggle off); rate-limit-class (`RATE_LIMITED` type or secondary-limit message + `retry-after`) → wait-and-retry per §5.5. Exact `type` strings for the deleteIssue mutation come out of probe P6/P9; do not hardcode beyond NOT_FOUND without probe evidence.

## §7. The capability contract (provider abstraction inputs)

### 7.1 Other-tracker deletion semantics — headline survey (so the contract isn't GH-shaped)

| Tracker | Can delete issues? | Gate | Soft or hard? | Source (retrieved 2026-06-11) |
|---|---|---|---|---|
| GitHub | Yes (GraphQL-only API) | Personal repo: owner account only. Org repo: admin/owner role + org-owner opt-in toggle (default OFF) | **Hard** (permanent; no user-facing restore; 410 Gone afterward) | §§1–4 above |
| Jira Cloud | Yes | "Delete Issues" project permission (permission-scheme-assigned; conventionally admin-only) | **Hard** — no recycle bin / undelete in native Jira Cloud; community guidance is "use a cancelled status instead" | https://support.atlassian.com/jira-cloud-administration/docs/manage-project-permissions/ ; https://community.atlassian.com/forums/App-Central-articles/Jira-Cloud-vs-Data-Center-How-to-Delete-and-Restore-Issues/ba-p/2940571 |
| GitLab | Yes | "Prerequisites: You must have the Planner or Owner role for a project." ("Required role to delete an issue changed from Owner to Owner or Planner in GitLab 17.7.") | **Hard** ("Delete issue" is permanent per docs flow) | https://docs.gitlab.com/user/project/issues/managing_issues/ § "Delete an issue" (quoted verbatim from fetched page) |
| Linear | Yes | member action (no admin gate documented at headline level) | **Soft** — "Recently deleted issues are stored in the archives for 30 days, after which they'll be permanently removed"; restorable from trash within the window | https://linear.app/docs/delete-archive-issues |

### 7.2 Minimal capability declaration the survey supports

The four backends span the full semantic space: hard-delete-with-role-gate (GH, Jira, GitLab), soft-delete-with-window (Linear), and the implied fourth state "cannot delete" (any backend where the permission is withheld — Jira/GitLab non-privileged contexts; the BD-212 charter's documented fallback). The minimal non-GH-shaped declaration is therefore:

- `issues.delete` ∈ { `hard`, `soft`, `none` } — what the backend's delete primitive IS. `soft` carries `issues.delete.recovery_window` (Linear: 30 days). `none` triggers the charter's documented fail-loud fallback (close + void-label).
- `issues.delete.requires` — opaque, provider-worded gate description used in error/help text (GH: "repository admin (personal: owner account; org: admin + org toggle)"; GitLab: "Planner or Owner role"; Jira: "'Delete Issues' project permission").
- `issues.delete.preflight` — a provider-implemented READ-ONLY probe returning pass/fail/indeterminate. **GH implementation, schema-verified 2026-06-11:**

```
$ gh api graphql -f query='... __type(name: "Repository") ...' --jq '...viewerPermission / viewerCanAdminister...'
{"description":"Indicates whether the viewer has admin permissions on this repository.","name":"viewerCanAdminister","type":{"kind":"NON_NULL","name":null,"ofType":{"name":"Boolean"}}}
{"description":"The users permission level on the repository. Will return null if authenticated as an GitHub App.","name":"viewerPermission","type":{"kind":"ENUM","name":"RepositoryPermission","ofType":null}}
```

  `repository.viewerCanAdminister` (Boolean!) is the cleanest admin preflight; `viewerPermission == ADMIN` is the enum equivalent. CAVEAT carried from §2.1: on org repos the org toggle is a second gate invisible to this preflight — preflight pass is advisory; the mutation's FORBIDDEN-class error remains the authoritative gate (fail-loud path must exist even after preflight pass). Also note `viewerPermission` "Will return null if authenticated as an GitHub App" — prefer `viewerCanAdminister`.
- `min_write_interval_ms` — already a provider concept per the charter; for GH it must be **≥ 1000** per §5.4 (this single field kills the BD-103 100ms value).

### 7.3 Marker-scoping is a VERB property, not a capability

The "only `<!-- pack-id: -->`-marked issues are deletable" guarantee cannot come from any tracker's permission model (no backend has per-issue-body ACLs). It is structural in the verb: the candidate set is built by marker query, and the delete loop's input is that set ONLY — a decoy can never enter it. Probe P10 verifies this structurally.
